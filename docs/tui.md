# Management Console (TUI)

`mmla tui` opens a terminal console that configures, launches and monitors every OpenMMLA component, on this machine or on remote machines over SSH. It is the primary entry point: the old per-pipeline shell scripts are gone, and everything the console launches is also an `mmla` command you can run by hand (see the pipeline guides).

## Install and start

Install the [prerequisites](prerequisites.md) first. The console runs from a clone of the repository, because it edits the configs under `pipelines/` and `config/` and runs the compose files under `docker/`.

```bash
git clone https://github.com/ucph-ccs/OpenMMLA.git
cd OpenMMLA
conda create -n tui python=3.10 -y
conda activate tui
pip install -e '.[tui]'
mmla tui
```

- With an editable install the console finds the repository root from the installed package, so `mmla tui` works from any directory. The package is also on PyPI (`pip install "openmmla[tui]"`), but a non-editable install has to be started from the repository root, because the console reads `pipelines/`, `config/` and `docker/` from the current directory in that case.
- Press `q` to quit. Four tabs sit at the top: **Environment**, **Launcher**, **Sessions**, **Status**.
- Every value whose key is named `token`, `password`, `api_key`, `secret`, `secret_key` or `subscription_key` is stored as `ENC(...)`: encrypted with the master key of the machine the file is on, and decrypted by the services there at startup. Every machine has its own key, a Fernet key in `~/.openmmla/master.key` (`0600`) made the first time something encrypted is written to it; a colleague's computer running its own console is no exception. The console re-encrypts secrets for the machine it writes to, and never copies or replaces a key (see [One master key per machine](system_services.md#one-master-key-per-machine)). Back the key up with its machine; without it the encrypted values stored there cannot be read.

## Hosts

Both the Environment tab and the Launcher have a **Host** selector: `Local`, or one of the SSH profiles defined under **System Settings → Hosts → SSH Profiles**. Every action then runs on that host, and every path is resolved as `<remote_project_path>/<same path relative to the repository root>`, so the remote machine needs a clone at the path the profile names. The `↻` button next to the selector tests every profile; a host that fails the test is shown as `(offline ✗)` and cannot be selected until it answers again. Profiles are re-tested every 30 seconds. The selector always lists this console's own profiles, also while System Settings → SSH Profiles shows another host's.

In the Launcher every leaf of the tree has **its own host**, because the parts of a deployment rarely share one machine: the AI servers sit on a GPU server, the bases on the base stations, the databases somewhere else again.

- A **pipeline, collection or MLLM Server** card opens on the host it was last pointed at, `Local` the first time. The choice is kept per card in `config/launcher_hosts.yml`, across restarts. If that host is offline or its profile is gone, the card opens on `Local` and says so in the log; the remembered host is kept for next time.
- A **System Services** card opens on the machine System Settings put the service on: the address (`InfluxDB.url`, `Gateway.host`, ...) is matched against this machine (its names and its addresses) and against the saved SSH profiles. This is a default, not a lock: pick another host to start or stop the service somewhere else for once. The card then says that the pipelines are configured for another machine and reports the chosen host's own port, and it is back on the configured machine the next time it is opened; to move a service for good, change its address in System Settings. An address that matches no profile, or a profile that is offline, opens the card on `Local` with the reason in the log. A `localhost` address names no machine, so that card remembers its host like a pipeline card. Nor does an address that still reads `<uber-server>` (not filled in yet, see [A new machine](system_services.md#a-new-machine)): that card also stays on the host it was last pointed at, says `System Settings → Connections → Redis has no host yet`, and reports the port of the host it is on; the placeholder itself is never looked up.
- Every **System Settings** form but Sudo has a selector of its own, one shared between them: it picks whose settings the forms show and save, and starts on `Local` with every new console. **Sudo** is this machine's alone (a remote host's `sudo` prompts are answered with its SSH profile's password), and **Session Control** has no host at all; they show a note with the reason instead of the selector.

The `[E]` and `(R)` markers in the tree follow the same rule: each leaf is checked on its own host, and a system service at the address the pipelines use, so the sidebar describes the deployment and agrees with every card that sits where it opened.

A remote host has to offer a **POSIX shell** over SSH: Linux, macOS or a Raspberry Pi. Everything the console does there goes through `bash -lc`, tmux, conda and the usual `test` / `cat` / `mkdir -p`, and the recorders use POSIX file locks and signals. A Windows machine answering with `cmd.exe` or PowerShell (Windows' own OpenSSH server) is recognised the first time it is picked: the selector goes back to where it was, the log says why, and the host is labelled `(Windows: not supported ✗)` from then on. With WSL2 as that machine's SSH shell it answers as Linux and works for server-side services (the AI stacks, the databases); cameras and microphones are not visible inside WSL, so it cannot record a collection session.

Once a session has been started, a remote host needs the same things a local one does for the components you launch there:

| You launch | The remote host needs |
|---|---|
| ASR / IPS / VFA bases, camera tools | conda with the pipeline environment and the repository at `remote_project_path`; an ASR base also FFmpeg and PortAudio. The Environment tab creates the environment and installs what the host lacks (**Install Tools**) |
| MLLM Server | conda with the `vfa-vllm` environment, tmux, the repository at `remote_project_path` |
| ASR Server / VFA Server, InfluxDB / MongoDB in `docker` mode | Docker Engine with compose, the NVIDIA container toolkit for the AI stacks, the user in the `docker` group, the repository (for `docker/`) |
| System services in `native` mode | `make` and `sudo`, and tmux for the dashboard, its worker and a native MediaMTX, which run in it; Redis, Mosquitto and Nginx are installed by Start when the host has none (brew on macOS, apt on Debian and Ubuntu), InfluxDB and MongoDB natively need their vendor repositories (see [System Services](system_services.md)) |
| Streams | `ffmpeg` and `tmux`; Start installs them when the host lacks them (apt on Debian and Raspberry Pi OS, brew on macOS; see the Streams tab below) |
| Collection Session | only `python3` and `ffmpeg`; the recorder code is pushed to `~/.openmmla/collection-runtime` automatically. A Mac also needs someone logged in on its screen, with Terminal allowed to use the camera and the microphone (see below) |

## Environment tab

A table of the conda environments OpenMMLA uses, on the selected host, with columns `Conda Env`, `Dep Group`, `Python`, `Status`, `System`, `Description`:

| Conda env | Extra in `pyproject.toml` | Python | Used by |
|---|---|---|---|
| `asr-base` | `asr-base` | 3.10 | ASR base station |
| `vfa-base` | `vfa-base` | 3.10 | VFA base station |
| `vfa-vllm` | `vfa-vllm-runtime` | 3.12 | local vLLM runtime for the MLLM Server card |
| `ips-base` | `ips-base` | 3.10 | IPS base station |
| `uber-base` | `uber-base` | 3.10 | analytics and session exports |
| `uber-server` | `uber-server` | 3.10 | dashboard, Celery worker, Nginx render step |
| `tui` | `tui` | 3.10 | this console |

The ASR and VFA server services have no conda environment any more; they run as Docker images (see the [Docker guide](docker.md)).

`Status` is computed live from the `[project.optional-dependencies]` groups in `pyproject.toml`: `Missing` (no such env), `Partial: pkg, pkg +N` (env exists, packages missing), `Ready`.

`System` is what the environment's programs need of the host and the host lacks: `lacks ffmpeg, portaudio`, `ok`, `-` for an environment that needs nothing of its host, or `?` when the host did not answer. `asr-base` needs FFmpeg, through which an ASR base pulls its stream, and PortAudio, which PyAudio is built against (on Linux also a C compiler, `build-essential`); `uber-base` needs FFmpeg for the session commands; `uber-server` and `vfa-vllm` need tmux, which the dashboard, its worker and the MLLM Server run in; `tui` needs git, and sshpass while an SSH profile signs in with a password. The VFA and IPS bases read video through OpenCV, which brings its own FFmpeg. The host is asked at **Connect** and **Refresh** with the PATH of what the console runs there over SSH, Homebrew's folders included, so a tool that is installed but off that PATH reads as lacking, as it would to a launch.

The buttons run these commands, locally or over SSH:

| Button | Command |
|---|---|
| **Create Env** | `conda create -n <env> python=<version> -y` |
| **Install Deps** | `conda run -n <env> pip install -e '.[<group>]'` in the repository; what the host lacks of the env's `System` needs is named first |
| **Install Tools** | installs what the selected env lacks (`System`): `apt-get install` through `sudo` on Debian, Ubuntu and Raspberry Pi OS, which is handed the SSH profile's password (on this machine the Sudo password of System Settings) on its input, never on a command line; `brew install` on a Mac. One install runs on a host at a time, the Streams tab's included (a second press while one runs there is refused), and the column is read again afterwards |
| **Delete Env** | `conda env remove -n <env> -y`, after a second press to confirm |
| **Git Clone** | remote hosts only: `git clone <origin url> <remote_project_path>` |
| **Git Pull** | remote hosts only: `cd <remote_project_path> && git pull` |
| **Git Pull All** | the same pull on every SSH profile at once, whatever the Host selector says: offline and Windows hosts are skipped, each host's output is shown in one piece as it finishes, and a last line sums up which hosts pulled, were already up to date or failed. This machine is left alone |
| **Connect** / **Refresh** | test the host and re-read `conda env list` / `conda list` |

A command console at the bottom shows the output and accepts ad-hoc shell commands on the selected host.

## Launcher tab

The sidebar is a tree; selecting a leaf shows its form or service card on the right. Leaves that launch something carry markers explained by the legend above the tree, `[E] env  [C] config  (R) running`:

- `[E]`: the conda environment on that leaf's host. Green `Ready`, yellow `Partial`, red `Missing`. Not shown for services that run in Docker or as native system services. A host's envs are read once and kept; the markers catch up when the Environment tab creates, removes or fills an env on that host, and when the Launcher comes back into view a minute or more later.
- `[C]`: whether the config file the leaf needs exists on that leaf's host: the pipeline's `config.yml`, and for the Gateway, Dashboard and Stream Server cards `nginx/config.yml`, `dashboard/flask-backend/config.yml` and `mediamtx/mediamtx.yml` under `pipelines/uber-server`. Green present, red missing. A remote host's files are looked up over SSH with the status probe (when the Launcher opens, when a host is picked or comes back online, after a Start or Stop), and a Save, or a Sync to Host or Sync from Host that copies one there, turns its marker green at once; until a host has answered, its leaves show no `[C]`.
- `(R)`: the service is running, according to the last status probe.
- `@ host`: where the system services run. The **System Services** heading names the host most of them share (`System Services @ <host>`, the machine System Settings put them on), and a service that runs elsewhere names its own on its line (`Redis (R) @ <other-host>`); a host that is offline reads `@ <host> (offline)` in red. It appears once the first status probe has placed them.

```
OpenMMLA
├── System Settings
│   ├── Hosts:        SSH Profiles
│   ├── Study:        Experiments, Tasks
│   ├── Connections:  InfluxDB, MongoDB, Redis, MQTT (Mosquitto),
│   │                 Gateway (Nginx), Stream Server (MediaMTX), Dashboard (Flask)
│   └── Credentials:  Sudo (local admin)
├── System Services
│   ├── InfluxDB, MongoDB, Redis, MQTT (Mosquitto)
│   ├── Gateway (Nginx), Stream Server (MediaMTX)
│   └── Dashboard (Flask), Dashboard (Celery)
├── Collection
│   └── Collection Session
└── Pipelines
    ├── ASR:  ASR Base, ASR Server
    ├── IPS:  IPS Base, IPS Intrinsics, IPS Transforms
    ├── VFA:  VFA Base, VFA Server, MLLM Server
    └── Session Control
```

A system service has one name everywhere the console shows it (its card, the sidebar, the Status tab, the log): `Role (Product)`, where the role is the **Connections** form that holds its address. `Gateway (Nginx)` and `Stream Server (MediaMTX)` each have a form of their own, since the load balancer and the stream server need not share a machine; `Dashboard (Flask)` and its worker `Dashboard (Celery)` take their host from `Dashboard (Flask)`, and the broker behind the `MQTT` section is `MQTT (Mosquitto)`. The two groups list them in the same order. The rest of this page uses the product name alone where the text is about the program (`make nginx`, the MediaMTX ports).

### Service cards

Every launchable leaf opens a card with the service name, its conda env and launch type, a status line, its parameters, and the buttons **Start**, **Stop**, **Logs** and **Refresh**. Bases and camera tools open in terminal windows and therefore show `Interactive (runs in its own terminal)` and no Stop button: what a base card starts exits by itself at its session's STOP (see [Pipelines](#pipelines)), and the camera tools are closed from their own window. On a Mac each window is named as soon as it opens, `IPS Base · base 1 @ mac-01`, starts with a banner in its pipeline's colour (ASR blue, IPS green, VFA magenta) and keeps its Terminal profile's own colours, since a program names its window itself only once its imports and set-up are done, which can take a minute, and the tabs of a window group show the running process rather than a name. Its shell is handed a short line that runs the component's command from a file only you can read: a longer line typed into a shell that is still starting is cut at 1024 bytes by macOS, Enter included, and never runs. The file is kept a day, so Up and Enter in that window start the component again. Cards for a pipeline also have a **Config** tab that edits `pipelines/<pipeline>/config.yml` on the selected host, with **Save** writing it back (and, on a remote host, copying it there).

Output of every action goes to the command console at the bottom of the tab. It is one transcript for the whole tab, since a build or a remote stop keeps printing after you move to another card; a divider such as `── Stream Server (MediaMTX) · Local ──` is drawn before the first line that belongs to another card or host.

**Sync to Host** and **Sync from Host** sit side by side, after one host picker, under the Config tab and under the Prompts, Action Schema and Transform Matrix tabs beside it, under the MediaMTX config of the Stream Server card, on Calibration Cameras, on the MLLM Server form, and on every System Settings form but Sudo. What a tab shows belongs to the host the Host selector names, and the picker names the other machine: every other SSH profile, and `Local` as soon as the tab is showing another host's files; it opens on `Select host...` with nothing picked. **Sync to Host** copies what the host on screen has saved to the host picked; **Sync from Host** copies the picked host's over the one on screen, and the tab is then read again, so it shows what landed, with the status line below it. A config put right on `<host>` comes back here, or goes on to a third host — between two remote hosts it travels through this machine, the one place both are reachable. What lands is the same file at the same place in that host's project, and the rest of what is there is left alone; a config that comes back brings that host's values with it, System Settings sections included, so read them over before a Save sends them out again.

What moves depends on the place. The Config tab and the MLLM Server form move the whole file as it was last saved: a Sync from Host replaces the `config.yml` of the host on screen, its `Bases`, `Streams` and devices included, and edits not saved there are gone once the tab is drawn again. The Prompts, Action Schema and Transform Matrix tabs and the MediaMTX config add or overwrite files by name and delete none; on Prompts and Transform Matrix a Sync from Host first lists the picked host's files, and says whether that host could not be asked or has none to give. Calibration Cameras moves camera parameters, not files (see [Pipelines](#pipelines)). Of the System Settings, Experiments moves its whole file, Tasks the task files by name, SSH Profiles merges profiles by name, and a Connections form moves its one section (see [System Settings](#system-settings)).

Syncs to one host wait for each other, and for a Save of a config or System Settings form there, instead of cancelling each other, and a remote file is written next to itself as `<file>.tmp` and then moved over the old one, so a dropped connection never leaves half a file; a `.tmp` file left on a host comes from such a copy and can be deleted. The encrypted values of a file are re-encrypted with the destination's own master key on the way, and the rest of the file stays as it was; a file holding a value none of the machines involved can open is not copied. Some of these files are tracked in git: the prompt templates, `config/vfa/action_schemas.yml`, `config/mllm_server.yml`, `config/tasks/*.yaml` and `pipelines/uber-server/mediamtx/mediamtx.yml`. A synced copy is a local change in that host's checkout, and a **Git Pull** there (Environment tab) stops on it when the pull changes the same file, until the change is committed or undone.

Before a Start the console checks that `config.yml` exists on the target host, that the sections managed by System Settings are up to date, and that the conda environment exists; a base card also asks the Stream Server whether the streams its bases pull are live (see [Pipelines](#pipelines)). The Gateway (Nginx), Dashboard (Flask) and Dashboard (Celery) cards need a `config.yml` too (`pipelines/uber-server/nginx/` and `pipelines/uber-server/dashboard/flask-backend/`, gitignored like every config, so a freshly pulled host has none): Start stops with a note when the card's host lacks it. Write it there with **Save** on that card's Config tab, or copy this machine's: **Sync from Host** with `Local` picked on that host's Config tab, or **Sync to Host** with Host = `Local`. Start is also refused, on any host, while a section the pipeline's config carries has no address yet (`IPS Base not started: System Settings → Connections → MQTT has no host yet. ...`): a service would connect to no machine. On a remote host whose config is out of date, the first Start only pushes the current System Settings and prints `Relaunch <service> once the sync above completes.`; press Start again. This is by design.

### System Settings

Every machine's services read **that machine's** settings: its pipeline `config.yml` files and, on top of them, its `config/system_services.yml` when it has one (see [System Services](system_services.md#pointing-the-pipelines-at-the-services)); and a console started there reads that machine's SSH profiles, experiments and tasks. Every System Settings form but Sudo therefore has a Host selector, one for all of them. On `Local` they edit this machine's project. On another host they read that machine's files over SSH (`Reading ... of '<host>' ...` while that runs) and say above the form whose they are; a Connections form also says where its values come from: its own `config/system_services.yml`, else its pipeline configs, else the defaults. **Save** then writes the section on that machine, into its settings file (created if it has none) and into its pipeline configs that carry it, and every change made in the Experiments, Tasks and SSH Profiles forms is written there at once (`Saved to <host>:~/OpenMMLA/config/experiments.yaml`); a write that fails says why, and the form is read from that host again. Flip the selector to check what a host will really connect to before a session.

A form acts on the host it was read from: when that host goes offline, or its profile is removed, before a Save or a sync, nothing is written and the status line says so; the next form opened falls back to `Local`. A file that cannot be read, as opposed to one that is not there (unreadable, not YAML, not what the form edits, or a broken task file), is never shown as empty, since the next change would write over it: a red line says why, with neither form nor sync row, and opening the form again reads it again. A Connections form whose `config/system_services.yml` cannot be read shows what that host's pipeline configs say, read-only: Save and Reset to Defaults are disabled, and there is no sync row. Experiments, Tasks and SSH Profiles refuse a sync while changes made in their form are still on their way to either machine (`Changes made here are still being written to <host>; sync once they are`).

A Start on a remote host keeps its pipeline configs in step first: with that host's own settings where it has them, section by section, and with this machine's everywhere else, leaving out a section this machine has not filled in. When a host's own settings differ from this machine's, the first Start there says which sections do. Write addresses that are true from every machine (a host name, not `localhost`) whenever more than one machine is involved.

Only the Sudo form is this machine's alone, and says why in the Host bar: the sudo password is this machine's (a remote host uses the password of its SSH profile).

**SSH Profiles**: one entry per remote machine, saved to `config/ssh_profiles.yml` (gitignored; `config/ssh_profiles_template.yml` is the tracked example). Fields: `Profile Name`, `Host`, `User`, `Port` (22), `Password` (needs `sshpass` on this machine; leave empty for key auth), `Key Path` (for example `~/.ssh/id_ed25519`), `Remote Project Path` (default `~/OpenMMLA`, must be the repository root on that machine). **Test Connection** checks the login and, when a password is stored, the password on its own: a key in the host's `authorized_keys` logs in whatever the password says, while `sudo` on that host asks for the account's real one, so a placeholder left there passes the login and fails the first Start that needs `sudo`; the result says which. Passwords are stored encrypted. With the Host selector on another machine the form shows that machine's `config/ssh_profiles.yml`, the machines a console started there can reach. Every change is written there at once, as the whole file, its passwords encrypted with that machine's own key and `chmod 600`, and changes nothing in this console: the Host selectors keep listing this console's profiles, and a rename there does not move the cards pointed at that name. The Test buttons test from this machine and report in the form only. **Delete** asks first, in the status line below the form, and deletes at a second press of the same row. A password that machine's own key cannot open shows empty, with `encrypted on <host>` in the field, and is kept unless a new one is typed; an entry the form cannot show (no name or host, or a port that is not a number) is written back as it was. Every host's list can be edited, whatever its key. **Sync to Host** and **Sync from Host** merge by profile name and ask for a second press first (`Press again to write 3 profile(s) (1 with passwords) into <host>'s config/ssh_profiles.yml.`): a profile of the source replaces the destination's of the same name or is added, and the destination's other profiles stay. A profile the destination already has keeps its own `Key Path` (a file on that machine), and its own password when the incoming one is empty or none of the machines involved can open it; a new profile whose password none of them can open arrives without one, and one whose `Key Path` names a file on the source is named in the status line. A profile sync hands passwords over: they are re-encrypted with the destination's key, and whoever holds that key can decrypt them. A sync into `Local` refreshes the Host selector and tests the profiles. A `config/ssh_profiles.yml` that cannot be read is shown as an error, never as an empty list.

**Experiments**: the study registry in `config/experiments.yaml` (gitignored, template `config/experiments_template.yaml`). An experiment has an id, a title, a status and a task type; each participant has a `group_id`, the `tag_id` of the AprilTag they wear and a short appearance `description`. The active experiments and their groups populate the **Experiment Group** dropdown on the base and collection cards, and the descriptions feed the VFA prompts. Those dropdowns, the rosters and the participants a session writes into its MongoDB document (which takes them to every host) always come from this console's own file, whatever the Host selector says. With the selector on another machine the form shows that machine's file, the one a console there would offer, and its **Task Type** lists that machine's tasks; a host without the file gets one from the first change made there. **Sync to Host** and **Sync from Host** copy the whole file, like a pipeline config. It holds the participants' names and appearance descriptions, which are personal data: sync it only to machines that should hold them.

The **Experiment ID** starts the id of every session of the experiment (`<experiment>_<group>_<YYMMDDTHHMMZ>`), and with it the names of the session's folders. It takes up to 64 ASCII letters, digits, `_`, `-` and `.`, starting with a letter or digit; `exp_<YYYYMMDD>_<task type>` (`exp_20261001_wegrow`) is the form the dashboard reads a session's date and task from. The **Title** is only shown, here and in the experiment menus of `mmla ses-man` and of a base's Create New Session, and can change at any time. The id cannot, once a session carries it, since the session's id, folders and MongoDB document would not follow: the field is greyed out when a session in the shared MongoDB names the experiment, or a session folder in `artifacts/` or `collection/` of this machine or of the host on screen starts with `<id>_`. It stays greyed out while those are being asked and, for every experiment, when one of them cannot be asked (the status line names it). **Save & Back** asks them again before it changes an id, so a session started since the form opened keeps it too, and an id another experiment already has is refused. **Delete** asks first, in the status line below the form, and deletes at a second press of the same row; the question says how many sessions carry the id, or that this is not known yet. Those sessions keep the id, but `mmla ses-tidy` and the ASR card's Speakers no longer find their participants.

**Tasks**: the task definitions in `config/tasks/*.yaml` (tracked in git), edited as raw YAML. **Create** refuses a name that is already taken, and **Delete** asks first, in the status line below the form, and at a second press of the same row removes both `<name>.yaml` and `<name>.yml`. Only consoles read them (an experiment's Task Type). With the Host selector on another machine the form reads all of that machine's task files in one go and writes each change there, one file at a time; a task file there that is not valid YAML leaves the whole folder unread. **Sync to Host** and **Sync from Host** carry every task of the source by name: the file the source reads for a task lands as `<name>.yaml` in the destination's `config/tasks/`, added or overwritten, and nothing is deleted there; a `<name>.yml` the destination also has is named in the status line, since the `.yaml` now comes before it.

**Connections**: `InfluxDB`, `MongoDB`, `Redis`, `MQTT (Mosquitto)`, `Gateway (Nginx)`, `Stream Server (MediaMTX)` and `Dashboard (Flask)`. Saving writes the section into `config/system_services.yml`, where the sections already there stay as they are and no section is added that nobody saved, and copies it into every pipeline `config.yml` that carries it (a missing config is not created, and one that cannot be read is named and left as it is); the pipeline Config tabs then show those fields read-only with a `managed in System Settings` note. A section no pipeline config carries (Dashboard: the console places and probes the Dashboard cards with it and passes the port to `make flask`) goes into that file alone. A pipeline that must keep its own value lists the section under `SystemServicesOverride:` in its `config.yml`, or presses `Override here` at the bottom of that section in its Config tab. An address nobody has filled in reads `<uber-server>` (see [A new machine](system_services.md#a-new-machine)), and a section with any such value counts as not set as a whole: on this machine Save keeps it in `config/system_services.yml` as typed, but the pipeline configs keep their own section and the services started here use theirs; on another host Save refuses it, as every sync does (a host on an older version would take the placeholder for a host name). The status line names the fields to fill. A stored secret, such as the InfluxDB token, shows as `ENC(...)`: the value encrypted with the master key of the machine the form shows; type the new value in plain text over it to change it, and Save encrypts it with that machine's key. The fields and defaults are listed in [System Services](system_services.md#pointing-the-pipelines-at-the-services).

Every Connections form has its sync row, on whichever host it shows. **Sync to Host** sends the section as the host on screen has saved it: a form with edits not saved says `Save first: Sync to Host sends what <host> has saved` and sends nothing. It writes the section into the picked host as a Save of that form there would: into the pipeline configs there that carry it, and into its own `config/system_services.yml`, created when it has none, without a trip through that host's form; its services and a console there then say what the host on screen says. **Sync from Host** reads the picked host's own section afresh (its `config/system_services.yml` first, else what its pipeline configs carry), writes it into the host on screen in the same way, and reads the form again. It is refused when that host's settings cannot be read, and when nothing but defaults or `<uber-server>` would come back. A secret such as the InfluxDB token is re-encrypted with the destination's key on the way; one none of the machines involved can open is not carried: the destination keeps its own, and the status line names it. A `localhost` value is copied as it is and then means the other machine itself; whenever a section crosses machines with one, the status line says so, since machines that share one service need its real host name here.

The Stream Server form is read by consoles only: it places and probes the MediaMTX card, and completes a stream written as a path, `ips/cam-1`, into the URLs of its `Streams` entry, which is what streams and bases use. No pipeline config carries it, so a console started on another machine reads that machine's own `config/system_services.yml`; the form follows the Host selector like the others, while this console places, probes and completes with **Local**'s address whatever the form shows. The [dashboard](dashboard.md#camera-tiles-and-live-video) reads it too, from the `config/system_services.yml` of the machine it runs on, to ask MediaMTX which streams are live and to tell browsers its WebRTC port; when that is another machine, **Sync to Host** gives it the address. Saving it with another address moves the stream URLs that named the old one in the pipeline configs of the host it is saved on (a remote host's in the same transfer as its settings file). Its **Sync to Host** and **Sync from Host** carry the address into the destination's `config/system_services.yml`, and the `Streams` entries of the source's pipeline configs into the destination's, merged by name: an entry of the source replaces the destination's entry of that name or is added, entries only the destination has stay, with their URLs moved along to the new address, and a host without that pipeline config is skipped and named (none is created); the rest of those configs is left alone. Sync from Host takes the address only from a host's own `config/system_services.yml` (one written before this section existed, which keeps it under `Gateway`, counts): its pipeline configs could only yield the Gateway's.

**Sudo (local admin)**: the sudo password of this machine, stored encrypted and never copied to another host: this form alone has no Host selector, and neither Sync to Host nor Sync from Host. Native Start/Stop of the system services run `make` with `sudo`, and the console types this password when the prompt appears (at most three times per command). Remote sudo prompts use the SSH profile's password instead.

### System Services

One card per system service: **InfluxDB**, **MongoDB**, **Redis**, **MQTT (Mosquitto)**, **Gateway (Nginx)**, **Stream Server (MediaMTX)**, **Dashboard (Flask)** and its worker **Dashboard (Celery)**. Installation is described in [System Services](system_services.md).

- **Host**: opens on the machine the service's address in System Settings names (`InfluxDB.url`, `MongoDB.url`, `Redis.host`, `MQTT.host`, `Gateway.host` for Nginx, `StreamServer.host` for MediaMTX, `Dashboard.host` for the dashboard and its worker), see [Hosts](#hosts). To run a service somewhere else for good, change its address in System Settings; the card follows.
- **Status** is a TCP probe from this machine to the address configured under System Settings, which is the path the pipelines take. The card description names the probed address. A `localhost` address names no particular machine, so it is probed on the card's selected host instead (over SSH for a remote host), and so is a card that was moved off the configured machine: it reports the host it is on, while the sidebar marker keeps following the configured address. An address that still reads `<uber-server>` is never looked up: the card says which form has no host yet and, as for `localhost`, reports the port of the host it is on. The Celery worker is detected by its tmux session. MediaMTX counts as running only when its RTMP **and** RTSP ports answer: an Nginx built with the RTMP module, the gateway of earlier versions, holds 1935 too, and would otherwise read as a MediaMTX that Stop can never find. When only one of the two answers, Refresh, Start and Stop say so in the log.
- **Start / Stop** on Redis, Mosquitto and Nginx run `make -C pipelines/uber-server <service>` / `stop-<service>` on the card's host; the make target installs the package first when that host has none (brew on macOS, apt on Debian and Ubuntu; `make` runs on the card's host, so it sees that host's platform) and rewrites the service's listener config to bind on all interfaces. Dashboard (Flask) runs `make flask DASHBOARD_PORT=<port>`, which opens a tmux session named `flask`; the worker opens one named `celery`. In both, `restart_on_failure.sh` starts the process again when it exits with an error, at most three times in a row (see [Running](dashboard.md#running)). On a remote host the same targets run in the command session below the card, as on Local, where the shell has conda; a `sudo` prompt there is answered with the SSH profile's password (the login password is what `sudo` asks for), on Local with the Sudo password of System Settings.
- **Run mode** (InfluxDB, MongoDB and MediaMTX): `docker`, the default, runs `docker compose -f docker/docker-compose.infra.yml up -d | stop | logs <service>`; `native` runs the make targets like the other cards. Choose `native` on a machine that still runs brew or systemd databases, otherwise Start brings up a container next to them. The choice is remembered per host for the current console session. MediaMTX in `native` mode runs `make mediamtx`, a tmux session named `mediamtx` around the installed binary.
- **Fetch Token** (InfluxDB, docker mode): reads the admin token of the compose stack on the selected host, from the running container or from `docker/.env`, and stores it encrypted as `InfluxDB.token`. Only the first and last four characters are shown.
- **Config** tab (Stream Server): the `mediamtx.yml` of the card's host as text, comments included, with a **Server-side recording** switch for `pathDefaults.record` (`sessions only`, as shipped: the paths of a running session, START to STOP; `every path`: every published stream) and a **Keep recordings for** choice for `pathDefaults.recordDeleteAfter` on top (three days as shipped; MediaMTX deletes a segment that long after it began, so a session's footage has to be exported before then, and `for ever` keeps everything). Both change the text in the editor, and Save writes it. A native MediaMTX reloads the file when it changes; one in docker (the default Run mode) reads it only when its container starts, so Stop and Start the card, and Send START again for a session that is running (a new start records none of its paths). A change to `readTimeout` or `writeTimeout` closes every stream and every pull as it takes effect, natively too, so make it between sessions (see [Streaming](rtmp_streaming.md#configuration)). A reload drops the recording START switched on for each path of a running session, so a few seconds after a Save or a Sync the console switches the paths of the running sessions on again, and the status line says which. Its **Sync to Host** and **Sync from Host** copy this one file between the card's host and the one picked, and the editor reads it again after a Sync from Host. Its address and ports for the console are under System Settings → Stream Server (MediaMTX).
- **Streams** tab (Stream Server): every stream of the IPS, VFA and ASR Base cards in one table, so that one left publishing is found without opening each card. It lists the `Streams` entries of the three cards (each read from the config of the host its card is on), the captures the stream registry notes as started from this console that no entry names any more, any `mmla-stream-<name>` tmux session a machine still has that neither knows of (started from another console), and every path the server receives that none of those accounts for. The table is asked for when the tab is first opened and at **Refresh**: each machine once over SSH, all at the same time (every SSH profile that is not Windows, and this machine; one the host check reports offline is not asked and reads `Offline`), the server through its API. What runs is listed first. **Pipeline** is the card whose `Streams` name it (`IPS`; a capture no entry names shows the first part of its path); **Machine** the SSH profile that runs its FFmpeg, or the address a path comes from when the console does not run it; **Capture** what that machine says, as on the card (`Running`, `Exited`, `Stopped`, `No answer`, `Offline`, `External`); **Stream Server** `● live` with how long it has been, `○ not live`, or `-` for a stream that goes elsewhere; **Readers** how many pull it now. A row `(in no Streams)` is a capture no entry names, there to be stopped, and goes once its machine has nothing left of it; `(not from here)` is a path the server receives from something the console does not run. `(name clash)` marks the rows of a name the cards give to another path on the server (another target, where it goes elsewhere), or run on more than one machine: a name is one capture, so the cards do not start such a stream until one of the entries is renamed (its target can stay); entries of two cards with the same name, machine and target are one capture and one row. **Stop** stops the selected capture the way its card does (Ctrl-C to FFmpeg, which finishes its recording, then the tmux session is closed; the log names the recording the stream's Start noted); on a path published from elsewhere it asks the server to close that connection, after which whatever publishes it may connect again. **Stop All** stops every capture still running or exited, on all machines at once, and takes a second press; paths published from elsewhere stay. **Logs** writes the last lines of the selected capture's pane into the log below. **Manage** opens the Manage of a pipeline card's Streams tab over the streams of every pipeline at once: what they recorded on each capture host (`record: true`), with the room left there, and **Delete File**, **Delete Day**, **Delete Older Than** and **Delete Expired** across all of them, each on a second press and never the file a stream is writing. A capture two cards name (an IPS and a VFA Base pulling one camera) is listed once. How long recordings stay is each card's (its own Manage's **Keep recordings for**), so this one offers no keep time; **Delete Expired** takes what is past each stream's own, the longer one where two cards name the stream. It lists what the table last read, so it opens once the table is filled. Streams are started on their own card.
- **Recordings** tab (Stream Server): what the server holds, path by path: the number of ten-minute segments, the first and the last, and their size on disk (read over a shell on the card's host, SSH for a remote one), with the free space of that disk, whether it records every path or the sessions' only, and the retention in force above the table. Below the table it says what it records now; a path it records that is publishing and has nothing written is shown in red. **Delete Path** removes every segment of the selected path, **Delete Older Than** every segment of every path that began before the chosen age; both go through the server's API, so they work for a docker and a native run alike, and both need a second press. Exporting a session's footage stays under Sessions: this tab is the server's inventory, not a session's.
- **Logs**: compose logs in docker mode; brew or journald logs for native services; the tmux pane for the dashboard, whose output is also kept in `pipelines/uber-server/logs/flask.log` and `celery.log` on its host.
- Nginx and the dashboard need the `uber-server` conda environment on the host, because the Makefile renders the Nginx config with it and runs gunicorn and Celery inside it. MediaMTX, the databases and the brokers need none (their cards say `env: none needed`).

### Collection

**Collection Session** records raw audio and video with FFmpeg for later replay through the pipelines with `source: file`. The card has an **Audio** and a **Video** tab, each with a recorder count, **Start Audio** / **Start Video**, **Stop**, **Stop All Hosts**, **Logs**, **Refresh**, **Download** and **Delete Remote**, a few fields, and under them a table of its recorders, one row per recorder (the count's + and - add and take rows away). The table works like the Streams tab of a pipeline card: click a cell, or press Enter on it, and its dropdown opens under it. Audio has the columns **Host**, **Device**, **Channel**, **Device Label** and **Participant**, Video **Host**, **Device**, **Device Label** and **Rotate**:

- **Session**: an existing session id, or `Create MongoDB Session` to mint one from the selected **Experiment Group** (`<experiment>/<group>`). A recording always belongs to a session MongoDB knows: an id that MongoDB does not have (it was deleted, or it is only known from artifacts on disk) is registered again under the selected Experiment Group when you press Start, and a session deleted in the Sessions tab is no longer offered here.
- **Output Root**: where every host writes its recordings (`artifacts`, which a remote host reads as `~/artifacts`), into `<session>/collection/<host>/`. The folder names the **machine** that records (this machine's short name, or the SSH profile), and each file names the **device** it came from after the machine: `<kind>_<host>_<device>_<start>.<ext>`. The session manifest carries both as `host` and `device`, so a session's folders read the same whether a Mac or a Pi recorded them.
- **Host**: the machine that recorder runs on, `Local` (this machine, where every new recorder starts) or an SSH profile (a Windows one is not offered). Recorders on one machine share it, so two microphones on `<host>` are two rows that both say `<host>`. A recorder moved to another machine loses its Device, which was the old machine's. The Host selector at the top of the Launcher plays no part in this card and shows `Per recorder` in its place.
- **Device**: what the recorder opens, from the microphones or cameras its Host has, asked over SSH for another machine the first time the list opens and kept until **Refresh**, with the tools the Streams tab uses (`arecord -l`, `hw:1,0`; `v4l2-ctl --list-devices`, `/dev/video0`; a Mac's `ffmpeg -f avfoundation -list_devices`, `:0` for a microphone and `0` for a camera). A microphone is listed with its input channels when its machine says how many (`hw:2,0  Jabra SPEAK 510 USB — USB Audio (1 ch)`): a Mac from `system_profiler SPAudioDataType`, Linux from `/proc/asound/card<N>/stream<M>` for a USB device, which is read without opening it, else from `arecord --dump-hw-params` (a device in use then says nothing). The Streams tab and the Config tab's device lists show the count too. **type another…** takes a device the machine does not list, and `-` picks none: that recorder asks for its device (and channel) in its terminal, as every recorder did before. Start refuses two recorders of one tab on the same device of one machine: one device is one FFmpeg (see below for its several channels).
- **Channel** (audio, once a Device is picked): which of the device's channels the recorder writes: `mix` (all of them averaged into one mono file, and the only choice for a one-channel device), `each` (a file per channel), `ch0`, `ch1` ... (one channel), or a list typed after **type another…** (`0,2`). Picking a Device sets `mix`, or `each` for a worn receiver (`vimo`, `badge`) of several channels. A device whose channel count is not known yet offers `mix`, `ch0` and `ch1`, and opening its Channel asks its machine; `each` needs the count, and Start refuses it without one. Start also asks a Linux machine for the count of a device it does not know yet (one a Device Label filled in), since ALSA opens a device with the number of channels it is given and FFmpeg asks for two when given none, which a one-channel `hw:` device refuses.
- **Device Label**: the name the recorder's files give its device, offering the devices the pipeline configs already name: the `Streams` entries of `pipelines/asr-base/config.yml` for a microphone (`jabra-1`, `jabra-2`), of `pipelines/ips-base/config.yml` and `pipelines/vfa-base/config.yml` for a camera (`c920-01` … `c920-12`). Recorder 1 opens on the first of them, recorder 2 on the second, and each is a device of its own, so four microphones on one machine are four names and not one. The number is the device's own, the same one its stream carries; it is not a base id (those are the `id` of the `Bases` entries, which a base keeps whatever device it reads) and not a tag id (`jabra-1` is a group microphone, bound to nobody). A single channel of a multi-channel device is appended, `vimo-0-ch1`, and a downmix is mono and appends nothing. The list is read from this checkout, whichever host a recorder runs on, since the devices are the deployment's. Picking a name whose `Streams` entry says which machine captures it (`c920-03`: `ssh_profile: <host>`, `device: /dev/video0`) fills that row's Host and Device from it, unless that cell was picked by hand on the row (a Device picked by hand keeps its Host too, as it is that machine's); the log says what it filled or kept, and a machine that is no SSH profile here is not put in. A device none of those configs name is typed after **type another…**, the last option (`badge-0`, `vimo-0`); it stays that recorder's when the card is drawn again. From a terminal the same thing is `mmla collect-audio --device-label badge-0` (`mmla collect-video --device-label …`), which takes any name. A recorder left on no device (more recorders than the configs name, or no list at all) falls back to the ffmpeg device (`/dev/video0` → `video0`, a Mac's first camera → `0`), which the file sources still read but which names no device. The recorder terminal prints the label it was given next to the device it takes, so a recording that is not what you meant is visible before it runs.
- **Rotate** (video): how the recorder turns the camera's picture, clockwise as the Rotate of a stream turns it: `0°` (as the camera gives it, where every recorder starts), `180°` (a camera mounted upside down, as the lab's C920s are), `90°` or `270°` (one on its side). Picking a Device Label whose video `Streams` entry has a `rotate` fills it from there, so a camera's recordings are turned as its stream is, unless the Rotate was picked by hand on the row (the log says what it filled or kept). FFmpeg turns the picture as it records, so the file is upright, and the recording's manifest entry notes the turn as `rotate`; a replay (`scripts/replay_sessions.py`) and `mmla ses-calibrate` read it, so the IPS and VFA bases turn the camera's intrinsics with that file's picture and report its poses in the sensor's frame (see [Calibrate from a recorded session](pipelines/ips.md#calibrate-from-a-recorded-session)). A turned recorder is passed `--video-rotate <degrees>` (`0°` passes nothing). From a terminal: `mmla collect-video --rotate 180`. Every Linux recording is written as 4:2:0 (`format=yuv420p`, after the turn): the camera's MJPEG is 4:2:2, which H.264 would otherwise keep and few players decode.
- **Participant**: whose voice each microphone records: a participant of the session's experiment group (`<name> (tag <id>)`), **Group (room microphone)**, or **bind later**. One channel is one person's microphone or the room's, so a recorder that writes several channels of its device (`each`, `0,1`) gets a row per channel right under its own (`ch0`, `ch1`), each with a Participant of its own, and its own row says `per channel`. A `jabra` opens on Group, and so does a label that a group base pulls; the other microphones open on the group's tag ids, lowest first, handed out in natural order of their file names (`vimo-0-ch0 < vimo-0-ch1 < vimo-1`). The group comes from Experiment Group for `Create MongoDB Session`, else from the picked session (an inactive experiment's too, and failing that from its MongoDB document). A pick is kept for that session and device (or channel), and never shows up in another session. Start is refused when one tag is picked on two rows or channels; a tag another host already bound in the session is only warned about. The pick goes into the recording's manifest (`participant`, `scope: personal`, or `scope: group`), and the session's MongoDB document notes `wearers` by device (a channel of a recorder of several under its own name, `vimo-0-ch1`), which a live ASR base pulling that stream reads (see [Personal microphones](pipelines/asr.md#personal-microphones-and-energy-attribution)). Without a participant list the Participant offers Group and bind later, and Start says so and goes ahead. From a terminal: `mmla collect-audio --participant 5` or `--scope group`, one per channel as `--participant 5,group,none`.

Each tab starts at one recorder; step the count down to zero to skip that role. A recorder with a Device starts at once and asks nothing (`--audio-interactive false --audio-device hw:2,0 --audio-channel mix --audio-channels 1`); one without asks for its device and channel in its terminal. The formats follow the host platform (`avfoundation` on macOS, `alsa` and `v4l2` on Linux). The channel prompt takes `mix`, one channel (`1`), or several of one device: `0,1`, or `each` for all of them. Several channels are one recorder: one FFmpeg reads the device once and writes one file per channel (`vimo-0-ch0`, `vimo-0-ch1`), all named with the same start, so they hold the same samples and lose the same ones if the device drops any. Two worn microphones on one receiver are recorded this way, never as two recorders on the same device: two FFmpeg processes each open it on their own, start at different moments and lose audio on their own. A dropped buffer does not shorten a file. FFmpeg's AVFoundation input on a Mac holds one buffer of about 10 ms and loses it when the next one arrives before FFmpeg has read it, and a WAV file keeps no timestamps, so without a fill each drop would move everything after it earlier than the video. Every recording therefore starts its filters with `aresample=async=1`, which writes silence wherever the input's timestamps jump ahead by more than 10 ms and drops audio where they fall more than 10 ms behind, and never stretches it: a file is as long as the time its timestamps cover. A recorder that asks in its terminal and is given several channels there asks the wearer of each channel too (the card's Participant is the first channel's default). From a terminal: `mmla collect-audio --device-label vimo-0 --channel 0,1 --participant 5,7` (`group` for a channel that is the room's, `none` for one left unbound). A recorder opens as a terminal window per instance and writes `manifest.yml` and `manifest.json` next to the files, with the shared `initial_sync_time` and ready-made `file_dir` values for the pipelines. When an audio recorder stops, it compares each file with the time FFmpeg spent writing it and adds the numbers to the file's manifest entry: `audio_seconds`, `wall_seconds` (from FFmpeg creating the file to closing it; where the file system keeps no creation time, as on Linux, from when the recorder saw the file appear), their difference `shortfall_seconds`, and `startup_seconds` (from the start stamp in the file name to the file's creation, the time FFmpeg took to open the device, so the first sample is about that much later than the stamp). A file shorter by more than 0.5 s or 0.1 %, whichever is larger, gets a note: it lost audio that its timestamps do not show, for example from a device that stopped delivering before the stop. The card reads `Running` for as long as a recorder process is alive on one of its hosts (this machine, the hosts its rows name, and the hosts this console started its session on), whichever session it records; **Logs** lists the live recorders of each of those hosts (role, session, pid), since each of them prints into its own terminal window.

On a remote Mac the recorder starts FFmpeg from a Terminal window on that Mac's own screen and prints its output in your terminal as usual; the window closes by itself once FFmpeg runs, so nothing stays on the Mac's screen and closing a window cannot end a recording. macOS lets an app use the camera and the microphone only once someone has allowed it to, and anything started over SSH counts as `sshd`, which is never even asked: FFmpeg would wait for frames forever, and record silence from a microphone without a word. Terminal on the Mac's screen is an app that can be allowed. So that Mac needs someone logged in on its screen, and Terminal enabled under **System Settings → Privacy & Security → Camera** and **Microphone** (the first recording asks there, on the Mac itself). The device choice stays in your terminal, and Ctrl+C there, Stop and Stop All Hosts stop that FFmpeg. Linux hosts and Raspberry Pis have no such permission: a user in the `video` and `audio` groups records over SSH directly.

One session is usually recorded by several machines: give each recorder its Host and press Start once. Start resolves the session first (`Create MongoDB Session` mints the id from the Experiment Group), then gets every remote host of the card ready at once (it checks SSH and copies the recorder code there, as a recording host needs no checkout) and opens one terminal window per recorder: this machine's recorders run here, a remote host's over SSH, each in the Output Root of its own machine. A host that cannot be reached is named in the log and left out, and the others record. **Start Audio** and **Start Video** start only the recorders of their own tab, so both tabs of one take are started one after the other, into the same session. What to know about it:

- The id is remembered by this console while it runs. After a restart, or from a second console, the card opens on `Create MongoDB Session` again; pick the running session from the list to join it. Creating a session for an Experiment Group that still has an active one says so in the log.
- A recording wins over the id on the card: while a host of the card records, the card opens on the session it records (the one the card shows, when a host records that), and the log says which hosts record it. A session picked by hand while they record (to download an older one) is left alone until the recording changes.
- **Stop** stops the session on every host of the card at once: the hosts its rows name, on both tabs, and the hosts this console started the session on. It marks the session ended in MongoDB unless one of those hosts still records it; **Stop All Hosts** reaches every other reachable profile as well.
- When the session is over (Stop, or Stop All Hosts), the card goes back to `Create MongoDB Session`, so the next Start is a new take. Stop, Download and Delete Remote do not need the id on the card: each host falls back to the session it recorded last. Picking an ended session by hand and pressing Start is held back once, with the choice spelled out: `Create MongoDB Session` for a new take, or Start again to record into it all the same (it becomes active again). **Stop All Hosts** stops every recorder of the session on every host (this machine, the hosts it was started on, and every other reachable profile; Windows hosts are left out), then marks the session as ended in MongoDB. **Delete Remote** removes the recordings of every remote host of the card from those machines after a second confirming press; the first names each host and session. With the default Output Root (`artifacts`) that is each host's `~/artifacts/<session>/collection/<host label>/`, and then the session's folder around it, once nothing but what the recorders write beside their recordings (the session's manifests) is left in it, also on a later press when the recordings went before; anything else in it (another host label's recordings) keeps it, and the log names what. With an Output Root of its own, the whole `<root>/<session>/` goes. It is refused while a Download of that session from one of those hosts is running (at either press, so a delete armed before the Download began is dropped), and a Download is refused while that folder is being deleted.

#### Downloading a session

**Download** copies the recordings of every remote host of the card into the local `artifacts/<session>/collection/<host>/`, one transfer per host, and merges the manifests; this machine's recordings are in place already. It takes each host's whole session folder, the audio and the video alike, whichever tab it is pressed on, and lists the files before it starts. A recording already here at the same size is not fetched again (a recording is named after the moment it started and is not written again once it is over), so a second press only brings what is new, plus the small manifests, which a stop rewrites in place. A progress bar appears under the command log while the transfer runs, showing the transferred and total bytes, the current rate and an estimate of the time left; **Cancel** next to it stops the transfer. **Sessions → Export** runs the same transfer for every host the session recorded on, with the rest of the session's data, and needs no card.

Files are staged under `artifacts/<session>/.staging/` and are merged into the artifact tree only once every file has arrived at its full remote size, so an interrupted download can never leave a truncated recording in `artifacts/`. If a download is interrupted — the network drops, you press Cancel, or you quit the console — the staged data is kept: press **Download** again and the transfer picks up where it stopped. Resume is byte-exact when `rsync` is installed on both machines; without it the console falls back to scp, which resumes file by file — the recordings that already arrived in full are skipped, and only a partly-written one is fetched again from the start. The log names the transport that was used. A second **Download** for a session and host that is already downloading is ignored.

A session that is still recording downloads as far as it has been written: the files that are still growing are named in the log and kept in staging rather than merged, because FFmpeg only finalizes a container when the recorder stops. Stop the recorders and download again.


#### Bringing earlier recordings in

Sessions recorded before the Collection card existed, or by hand, come in through `mmla ses-import`, which builds the same `artifacts/<session>/collection/<host>/{audio,video}/` tree and manifests from whatever a folder holds:

```bash
mmla ses-import -n "<folder>/session_<ISO>Z"        # -n shows the plan and changes nothing
mmla ses-import -g <group> "<folder>/session_<ISO>Z"
mmla ses-import --only session_<ISO>Z -g <group> "<folder>"   # a folder holding several sessions
```

It recognizes a video named by the local time it started (`<YYYY-MM-DD> <HH-MM-SS>.mov`, `record_<YYYYMMDD>_<HHMMSS>.mp4`; `--tz`, `Europe/Copenhagen` by default, says whose local time), a file already named with its unix start (`record_<unix>_<host>.mp4`, `audio_<unix>_ch0.wav`), and an ASR base's folder of three-second recordings (`badge_0/records/badge_0_record_<unix>.wav`, or `segments/` when the raw records were not kept), even downloaded twice. Continuous files are moved under their new names, a base's segments are concatenated into one file that starts when the session's first segment did (silence where nothing was recorded, so every base of a session shares one start; a base stamps each record with its machine's wall clock, so a gap that opens at the same moment and lasts as long in every base recording then is reported as a clock step, in the plan, in `import_report.json` under `clock_steps` and in each base's manifest notes: a step of that machine's clock, or all bases stopping at once, which only a continuous recording such as a camera's track can tell apart; `--close-clock-steps` takes such steps out of the stamps instead of filling them with silence, and a gap in one base alone stays a recording gap either way), a video's own audio track is extracted as a 16 kHz group microphone, and two videos of one camera recorded one after the other keep one host label. A name carrying two `<label>-<number>` parts gives both slots, machine first and device second (`pi-01_c920-01_<unix>.mov` → `video_pi-01_c920-01_<unix>.mov`, `pi-04_vimo-0_..._ch1.wav` → `audio_pi-04_vimo-0-ch1_....wav`); one part alone is the machine, and the device slot keeps a placeholder (`video0`, `mix`, `ch1`, `mic`) for `ses-tidy --device` to correct. The session id is `<experiment>_<group>_<start>` (`-e`, `-g`, or `-sid` outright), the start taken from a `session_<ISO>Z` folder name. Everything else in the folder (logs, frames, the old outputs, speaker profiles) moves to `legacy/` under the session, and `import_report.json` says what went where; `--copy` leaves the source untouched instead. A replay starts at the session's `initial_sync_time`, the latest start among its recordings, so a camera that started late shortens the replay of everything else.

`mmla ses-tidy` corrects an imported session afterwards, folders, file names and manifests together (the manifests are rebuilt from the tree at the end): `-e` / `-g` rename the experiment or the group (the session moves to `<experiment>_<group>_<start>`); `--host OLD=NEW` relabels a host (the machine folder; the device sits in the file names, see [Collection](#collection)), `--video-host` and `--audio-host` move only one modality (a camera's own audio track becomes the `jabra` group microphone); `--device [HOST/]OLD=NEW` renames the device in the file names, which is what the placeholders an import leaves need (`--device video0=c920-01`, `--device ch1=vimo-0-ch1`), `HOST/` holding it to one machine's files when two of them recorded a `mic` of their own; it runs after the host relabels, so name the machine as it is by then; `--crop HOST=NEW:X,Y,W,H` cuts a region of a host's videos out as the videos of NEW, for a recording that is a mosaic of several cameras (`--crop-fps 30` to lower the frame rate); `--flip HOST` turns a host's videos by 180 degrees (both re-encode with the Mac's hardware encoder, the original of a flip staying under `raw/`); `--to-raw HOST` keeps a host's files under `raw/`, out of the sources, and `--delete-host HOST` deletes them; `--tag-size` and `--note` go into the session manifest; `--same-class-as SESSION` marks another session of different pupils from the same school class, writing `same_class_as` into both manifests (the other one's too); the link survives rebuilds and follows a renamed session; `--pupils 0,1` declares the tag ids of the session's pupils, writing `pupils` into the manifest (with a dated note), which `mmla ses-fuse` takes as the session's pupils (see [Pupils](analytics/window_features.md#pupils)); they survive rebuilds, and `--pupils none` (or `''`) clears them; `--prune-legacy` keeps the speaker profiles (as `collection/<host>/profiles/`) and `meta.txt` and deletes `legacy/` and the old analysis folders (frames, logs, measurements, exports), which a replay produces again:

```bash
mmla ses-tidy <session-id> -e <experiment-id> \
  --crop cam-1=pi-01:0,0,960,540 --crop cam-1=pi-04:960,540,960,540 --crop-fps 30 \
  --device pi-01/video0=c920-01 --device pi-04/video0=c920-04 \
  --audio-host cam-1=jabra --to-raw cam-1 --tag-size 0.07 --prune-legacy
```

Every audio recording in the manifests has a `scope`, `personal` (a microphone worn by one person) or `group` (a room microphone), and a `participant`, the tag id of its wearer or null. The device name gives the scope: `jabra` and a camera's audio track are the group's, `vimo` and `badge` (also an imported `base-vimo-*` folder) a person's, and `mic`, `mix` and `chN` stay unknown until the device is renamed. `--scope [HOST/]DEVICE=personal|group` sets it by hand. `--participant [HOST/]DEVICE=TAG` binds a wearer and makes the microphone personal; `none` unbinds it. `--participants-in-order` tags the personal microphones in natural device order (`vimo-0-ch0 < vimo-0-ch1 < vimo-1 < vimo-10`) with the tag ids of the session group's participants in `config/experiments.yaml`, lowest first (the group after `-e`/`-g` when given): a microphone already bound to one of those tags (on the Collection form, or by an earlier `--participant`) keeps it, the others take the tags left, any beyond the list is left unbound, and every binding it changes is printed; for a group the file does not list it falls back to 0, 1, 2 ... and says so. A `--participant` given with it wins. A group microphone never keeps a tag. A device rename works its default scope out again (an explicit `--scope` stays) and keeps its tag, and the values survive later rebuilds. A live Collection recording notes the Participant picked on the form, else the default scope, and a rebuild keeps it; what the form left unbound is bound here. The ASR replay and the fusion read these values (see [Personal microphones](pipelines/asr.md#personal-microphones-and-energy-attribution)):

```bash
mmla ses-tidy <session-id> --device ch0=vimo-0-ch0 --device ch1=vimo-0-ch1 --participants-in-order --participant vimo-0-ch1=3
```

`mmla ses-align` puts a session's recordings on one clock and one start. A per-person microphone (badge, vimo) is stamped by the base that recorded it; a camera's file is stamped by whatever wrote it, to the second at best and after the delay of a stream. Both heard the same room, so the command cross-correlates every audio recording with the longest per-person microphone (`--reference HOST` picks another) and reports how far each one's nominal start is off, with a confidence (how far the correlation peak stands above the rest; below 8 the number is a guess) and a margin over the runner-up; two recordings of one base come out at 0.00, which is the check that the method works. `--apply` moves the recordings measured off by more than `--tolerance` (0.25 s) with confidence above `--min-confidence`, and moves a camera's video with its audio track since they share one start: every video that starts with the track to the millisecond, on any machine (a track filed under the Mac, `<host>/jabra-0`, and its video under the Pi; or the crops of one recording, as a mosaic cut with `ses-tidy --crop` gives its track and its cameras one start), so a track never moves without its picture. Nothing else moves along, and the output names every file that starts with it and stays: the reference, a per-person microphone (a take split can give a vimo the camera's start), and another audio recording (each goes by its own measurement). `--trim` then cuts every recording to the session's common start, the latest start among them: audio to the sample, video at the last keyframe before it (a stream copy, nothing re-encoded, so a video that starts before a microphone ends up at most one keyframe interval ahead of it), and names every file with its exact start. What came before the common start is gone.

`--end SECONDS` cuts the other side, for a session whose recordings ran on after the lesson: every recording of every host, audio and video, ends SECONDS after the common start (the latest start, the manifest's `initial_sync_time`, the reference `--trim` uses). Audio is cut to the sample; video by stream copy, which needs no keyframe at an end but stops in decode order, so a video may keep a frame or two past the cut (the manifest takes the length ffprobe reads). A recording that already ends by then, or within 0.25 s after, is left as is, so a second run cuts nothing. Unlike `--trim` this is reversible: the full-length originals move to `raw/<host>/<audio|video>/` (their place under `collection/`, out of the sources), and the manifests are rebuilt with the new lengths and `stopped_at` and a note naming the cut. `--dry-run` prints what `--end` would cut and changes nothing. `--end` alone measures nothing. The session's analysis outputs still cover the full length, so replay and fuse it again afterwards.

```bash
mmla ses-align <session-id>              # measure only
mmla ses-align <session-id> --apply --trim
mmla ses-align <session-id> --end 2400 --dry-run
```

What no shift of a start can fix is edited inside the audio files of `--devices` (`vimo-0-ch1`, `<host>/vimo-0`, several separated by commas): `--warp MAP` puts a file on the reference timeline with a piecewise time map, for two channels that lost audio on their own; `--cut-zeros TIME[:LENGTH]` cuts the digital-zero run that starts within 0.5 s of TIME in each file (all of it, or its first LENGTH), for the silence an import put in for a clock step, and refuses a file that has none there; `--cut START:END` (or `START+LENGTH`) cuts a stretch; `--cut-head SECONDS` cuts a file's first SECONDS and keeps its start, so the rest sits that much earlier, for a recording measured a constant time late (`--trim` is the head cut that keeps the timing). Positions are seconds into the file as it is, or sample indices with `--samples`. The map is a JSON file or inline JSON: `{"lags": [[time, lag], ...]}` says that from `time` on the file's content sits `lag` seconds later (the first lag holds from the start), `{"knots": [[t_in, t_out], ...]}` that the stretch from `t_in` to the next knot starts at `t_out`, with an optional `"note"` on how it was measured. For a lag track measured as "the other file hears each sound `lag` s later at time `t`", the late file goes onto the early one's timeline with knots `[t + lag, t]`, and the early file onto the late one's with `[t, t + lag]`; either cuts from the moved file what it heard while the other one dropped audio, so two captures that both dropped some go onto one insert-only timeline instead, one map per file whose lag never falls (each drop of either capture becomes silence in that capture). Nothing is resampled, which would change the pitch of speech: where the lag grows, silence is inserted, and where it shrinks, the samples that would land on audio already placed are cut. The start stamp in the name stays, the original moves under `raw/<host>/audio/` (a file edited twice keeps its first original there) with a `<name>.edits.json` of every edit beside it, and the manifests get the new length and a note with the numbers (the ranges cut, the knots, a summary of them when a map has more than 12, every knot staying in the `.edits.json`, and `--note TEXT`). `--dry-run` prints what would change, and the edits go without `--apply`, `--trim` and `--end`. Replay and fuse the session again afterwards.

```bash
mmla ses-align <session-id> --devices vimo-0,vimo-1,vimo-2 --cut-zeros <seconds> --cut-zeros <seconds> --dry-run
mmla ses-align <session-id> --devices vimo-0,vimo-1 --cut-head <seconds> --note "measured <seconds> s late against jabra-0"
mmla ses-align <session-id> --devices vimo-0-ch0 --warp <map-ch0>.json --dry-run
mmla ses-align <session-id> --devices vimo-0-ch1 --warp <map-ch1>.json --dry-run
```

### Pipelines

The ASR, IPS and VFA base cards share one shape:

- **Launch** tab: how many bases and synchronizers to start, the **Session** (an existing id or `Create MongoDB Session` from the **Experiment Group**), the mode for ASR and VFA (`live`, `capture`, `analyze`), the pipeline's toggles, and everything the processes used to ask in their own windows:

    - **Session**: one take is one session, however many cards and hosts start its bases. The first Start with `Create MongoDB Session` mints the id; from then on every base card (ASR, IPS and VFA, on any host) opens on that session, and so does the Session list of Session Control, so the other cards join it by pressing Start. The same goes for a Start into an existing session, a Collection Start, and a session picked by hand on a base card, `Create MongoDB Session` included: a new card or host keeps the pick. When the session ends (STOP in Session Control, Stop All Hosts on the Collection card, End Session or a delete in the Sessions tab), the cards go back to `Create MongoDB Session`, so the next Start is a new take. A Start into a session that has ended anyway (stopped from another console) is held back once, as on the Collection card: pick `Create MongoDB Session` for a new take, or press Start again to go on in it, which makes it active again. The followed session is kept by this console while it runs; after a restart the cards open on `Create MongoDB Session`, and the running session is picked from the list.
    - **Base 1**, **Base 2**, ...: which entry of the `Bases` list each base is, one dropdown per base. They follow **Num Bases**: `+` adds one, `-` hides the last and keeps what it had. The options are the entries of the config on the card's host, `0 · macbook-air · stream ips-cam-1` (the id, the camera of an IPS or VFA base or the `base_type` of an ASR one, the source and its index), and a base that pulls a stream the config's `Streams` no longer name says `(not in Streams)` after it: that is what the base would stop on, and its `Bases` entry is where it is repointed. Base *n* starts on the *n*-th entry, and a base the list has no entry for on `ask in its window`, which passes no `-b` and lets that base ask. Such a row takes its entry once the config has one (its first Save, or a **Refresh** that could read it); a row put on `ask in its window` by hand stays there. Start refuses two bases on one entry, which includes a base on `ask in its window` next to a base on the config's only entry: with one entry listed, a base given no `-b` takes that one.
    - IPS: the synchronizer's **Main Camera**, one option per `camera_sync/transformation_matrices_<id>.json` on the card's host, then each base no file there holds, of its own or in another main's matrices (`· alone, no matrices`: a session of that camera alone, in its own coordinates; Base 1 takes it along; Start refuses it beside other bases, see [One camera](pipelines/ips.md#one-camera)), starting on the `Bases` entry with `main: true` and following Base 1 to the main of its room; with rooms in `Bases`, **Room** puts a room's bases, their number and its main camera on the card, as a session is one room's (Start refuses bases of two rooms, or another room's main camera; see [Several rooms](pipelines/ips.md#several-rooms)). Start is refused while no Main Camera is picked, with the folder named: make the files with **IPS Transforms**, bring them to a remote host with **Sync to Host** on the Transform Matrix tab (each base needs its file too), then press **Refresh**. A Refresh that cannot list a remote host's folder keeps the Main Camera list and pick it had, and the console says the list may be out of date.
    - ASR: **Language**: the language the bases have their speech transcribed in (`-lang`), sent with every request to the speech transcriber, which keeps running whatever its own config says; the first option leaves it to the service. See [Language](pipelines/asr.md#language).
    - ASR: **Participant 1**, **Participant 2**, ...: under each Base, whom that base's speech is attributed to (`--participant`): a participant of the session's experiment group (a microphone they wear), **Group**, or **Speakers (speaker verification)**. A row opens on the pick kept for that experiment group and Bases entry, else on the wearer the session's Collection Start noted for the base's stream, else on what the base type's `asr_scope` says (`wearer`: the group's participants in row order; `individual`: Speakers; `group`: Group). Start is refused when one tag is picked on two bases. See [Personal microphones](pipelines/asr.md#personal-microphones-and-energy-attribution).
    - ASR: **Speakers 1**, **Speakers 2**, ...: under a base whose Participant is Speakers, the speaker profiles it recognizes (`-spk`): the participants of the session's experiment group that have a profile on the card's host, unless you tick them for that base under **Manage**, which also registers speakers (recorded from a base, or from audio files on this machine) and deletes them. Start is refused when such a base in `live` or `analyze` mode would have none. See [Speakers](pipelines/asr.md#speakers).
    - ASR and VFA: **Sync Waits For**, how many bases the synchronizer merges each time slice from (`--num_bases`), counted over every host of the session, not only this card's **Num Bases**. It goes along with Num Bases until it is set by hand, which it has to be when bases of the session run on other hosts. Too high, a slice waits for bases that never report and is merged only when it expires; too low, it is merged before the others report. Start refuses a card that starts more bases than the synchronizer waits for, and says so when the config lists more entries, or the synchronizer waits for more bases, than the card starts: those have to run on other hosts, in the same session. At 0 the flag is left out and the synchronizer counts the `Bases` entries of its config.

    The dropdowns follow a **Save** on the Config tab and a change of host, and **Refresh** reads the config and the matrix files again. Start opens one terminal window per instance, with the choices as flags: `mmla ips-base -sid <id> -b 0`, `mmla ips-sync -sid <id> -mc 0`, `mmla asr-sync -sid <id> --num_bases 2`. A process started this way asks nothing: it starts at once, waits for its session's START (Session Control), and exits when the session's STOP comes or its run ends. If it cannot start (a matrix file or a `Bases` entry that is not there), it says why in its window and falls back to its menu there, where it can be put right by hand. Run by hand without `-sid`, the commands ask as they always did. What a process writes for its session (its log, the config it ran with, what it recorded) stays on the machine it ran on, under `artifacts/<session>/pipelines/`; **Sessions → Export** brings it here.

    Before the windows open, Start asks the Stream Server of System Settings (its control API, `api_port`) which of the streams these bases would pull it receives now: the stream of each row's `Bases` entry whose `source` is `stream`, from the config on the card's host (for a remote host, the copy the card last read; Refresh reads it again). A base left on `ask in its window` while the config has several `Bases` entries (with one entry it is that entry, and its stream is asked about), one with a device of its own, a file or LSL, audio pushed straight to an ASR base over `udp://` or `tcp://`, and every base of an `analyze` run pull nothing a server could speak for, and a stream whose URL names another server is not asked about. With every stream live the log lists them and the bases start. The log says when it asks (`Asking the Stream Server (server-01) whether c920-01 is live...`), and every line of the answer names the card and the host it was pressed for. A stream that is not live holds the Start back once: the log names it, the bases that pull it (`Base 1 · entry 4`) and the machine that captures it (for a stream published from outside the console, it says to ask whoever publishes it), and, for one started from this console's Streams tab and not stopped since, when it was started (its FFmpeg publishes again by itself within seconds of a drop, so one that stays `○ not live` has stopped on its capture host or cannot reach the server). Start it on the Streams tab and press Start again once it reads `● live`, or press Start again at once to start the bases all the same: each waits for its stream for up to `connect_wait` seconds (30 by default, see [Streaming](rtmp_streaming.md#bases-pulling-a-stream)). The second press goes ahead for the same card, host and missing streams only (each card and host keeps its own), and comes before the question about a session that has ended. **Stop** on the card while the Start still waits for the answer calls that Start off. A Stream Server that does not answer within three seconds, or a Stream Server form with no host, holds nothing up: the log says whether the streams are live is not known, and the bases start.

    Each base notes in the session the machine, `record` and `rotate` of its stream as the `Streams` entry of its own config says (the config on the card's host, which is the one it reads), and what reads the session goes by that note: **Sessions → Export** asks the machine it names for the stream's recording, `mmla ses-calibrate` and the analysis report take the turn it gives, and the dashboard offers **Turn 180°** only on a camera noted as not turned. The configs are kept per host, so the Streams tab may have started a stream from another host's config. Start therefore also compares each stream these bases take (pulled, or pushed to an ASR base over `udp`/`tcp`) that this console's Streams tab started and has not stopped (the stream registry notes the machine, the recording and the turn of every Start) with its entry in the config of the card's host. A stream that runs on another machine than its `ssh_profile`, records while the entry says `record: false` or the other way round, or, for a camera, is turned otherwise than the entry's `rotate`, gets one yellow line in the log naming the card and the host, the stream, when it was started, what it runs with, what the config says and what the session will note instead (`IPS Base on this machine: c920-01, started from this console's Streams tab at 21:16, records on raspi5-01, but the config these bases read says record: false, so the session notes it as not recorded.`). On an IPS Base card the line of a camera turned otherwise adds that the bases read the config's turn as well, so they turn its intrinsics and poses for a picture that is not turned so (a half turn apart, its tags come out mirrored through the camera's axis), as the Streams tab's own note of such a camera says. A last line says how to make the two agree: **Sync from Host** or **Sync to Host** on the Config tab copies one host's config over another's, or change the entry, Stop the stream and Start it again on the Streams tab (a Start leaves a running stream as it runs); then Stop the bases if they run and press Start again. This only warns: the Start goes on as before, whether or not the Stream Server form has a host. A stream published from outside the console, one stopped since, and a stream registry that cannot be read say nothing.
- **Config** tab: the pipeline's `config.yml`. The sections that System Settings manage carry the same names as there (`Gateway (Nginx)`, `MQTT (Mosquitto)`), and the ones that only make sense together say how: `Gateway` is the Nginx load balancer, and each entry of `Server` either goes through it (a bare name such as `infer`, shown resolved: `through the Gateway: http://<host>:8080/infer`) or connects to a server directly (a full URL). `+ Add Stream` adds a `Streams` entry (on the ASR card with `kind: audio`) and, for ASR, `+ Add Base` adds a device type under `Base`. A stream's `kind` is a dropdown, `audio` or `video`; left empty, a sound device (`hw:1,0`, a Mac's `:0`) or a `udp://`/`tcp://` target makes it audio, and anything else is what the card is for: audio on ASR (a Mac's first microphone pushed over RTMP names no device), video on IPS and VFA. The Streams tab captures, records and files the stream by it. A few model and backend keys are dropdowns too: on the VFA Server card `backend`, `prompt_profile`, `image_detail`, `gaze_backend`, `gaze_model` and `features.pose_model`, on the ASR Server card `SpeechTranscriber.local.diarize_model`; a value not in the list (a local checkpoint) is shown, marked and kept, and the blank keeps the template's default. `Bases` entries are edited with dropdowns filled from the config (calibrated cameras, base types, sources, the other files of a file entry's folder, and for `source: stream` the pullable `Streams` entries, `ips-cam-1  (rtsp://…)`, stored by name; a stream added on the same tab is listed as soon as the config is saved, and one deleted there is marked on the entries still pointed at it, which keep it until they are repointed). An entry shows only the fields its `source` uses: `source_index` for a device index, a stream, an LSL stream or a file (**Browse…** writes the file's full path), `channel_select` for `pyaudio`, `port`, `host` and `packet_format` for `udp`/`tcp`, and `participant` (the wearer's tag id) for every source of an ASR base; the others are left out of the saved entry, and an entry that still says `channel` is shown, and saved, as `channel_select`. The devices themselves are found, not typed: once the form is up the console asks the card's host what it has (PyAudio's input devices for a `pyaudio` base, the cameras for an `opencv` one), over SSH for another machine. The `source_index` fields become dropdowns of what was found once the host answers, with a line under them saying what that was; a value the host does not list now (a device unplugged) stays as it is, marked, and a host that does not answer, or runs Windows, leaves the text box with the reason. The list is a snapshot, and **Refresh** on the Launch tab asks again. A stream's machine and device are not on this tab: the Streams tab picks them, and a Save keeps them. Once the form is up, and again each time the Config tab comes into view (a stream started on the Streams tab meanwhile), the console asks the Stream Server which of them are being published: `●` live, `○ … not publishing now`, no mark for a stream on another server; below them it lists the paths the server has live under the same apps that no `Streams` entry names, and says so when the server does not answer). The IPS and VFA forms show the config's `Cameras`, one group each: the calibrator writes them, **Calibration Cameras** brings them from another machine (**Sync from Host** there) or takes them to one (**Sync to Host**), and `+ Add Camera` adds one by hand (a name, then `fisheye`, `params`, `K` and `D`, the matrices written as bracketed rows). The template holds none, and the `camera_name` example that older configs got from it is dropped at the next Save. A group taken out with **Remove** (a camera, a stream, a base device) is taken out of the file at Save too. `rtmp` is not offered as a source: it is the old name of `stream`, and an entry that still says it is shown and saved as `stream`.
- **Streams** tab: the `Streams` entries of the config (they are defined on the Config tab, where `target` takes the path alone, `ips/cam-1`, and Save completes it with the Stream Server of System Settings; they belong to the pipeline because its bases read them from its config), with **Start**, **Stop**, **Logs**, **Probe**, **Start All** and **Stop All** (they wrap onto another line when the pane is too narrow to hold them side by side), and above them a **Recordings** row with **Manage**. The rows are listed by name, a number in a name counted as one (`cam-2` before `cam-10`), whatever the order of the config, and **Start All** starts them in that order. A row's **SSH Profile** is a dropdown (click it, or press Enter on the row): the machine that runs the stream's FFmpeg, `local`, an SSH profile, or `-` for a stream someone else publishes. Its **Device** is a dropdown too (click it): the microphones or cameras that machine has, by the stream's `kind` (`arecord -l` on Linux, `hw:1,0`; `v4l2-ctl --list-devices`, `/dev/video0`; a Mac's `ffmpeg -f avfoundation -list_devices`, `:0` for a microphone and `0` for a camera), asked over SSH for another machine the first time the list opens, and again after **Refresh**; `-` picks none, and Start takes the machine's first; **type another…** takes one the machine does not list. A device picked for one machine goes when the stream moves to another. Both picks are written into the card's config on its host; the Config tab does not show them, and its Save keeps them. A running stream keeps its machine until it is stopped, since Stop looks for it on the machine its SSH Profile names, and takes a new device at its next Start. Recording has two independent switches: a row's **Record** is a dropdown as well (click it), `yes` or `no`, which sets that stream's `record` (on the capture device, next to the push); and the Stream Server records on its side the paths of a running session, START to STOP (its card, Config tab; see [On the server](rtmp_streaming.md#on-the-server)). A row's **Rotate** is a dropdown as well (click it): how the capture host turns the picture, clockwise, `0°`, `180°` (a camera mounted upside down), `90°` or `270°`, which sets that stream's `rotate`; FFmpeg turns it there once, so the bases, both recordings and the dashboard get it upright, and the bases turn the camera's intrinsics with it (a microphone shows `-`, an external stream `n/a`). A stream keeps the Record and Rotate it was started with, so a running one is stopped first, and unlike the other two picks these do show on the Config tab, which is drawn again when a row changes them. The stream registry notes the turn each Start gave the picture (for a stream started before turns were noted, the machine's FFmpeg command line says, asked once per start), and a running stream whose config was given another turn since (on the Config tab, or from another console) shows both in yellow, `180° (runs 0°)`, and each **Refresh** logs one line about it: the bases read the config's turn, so until the stream is stopped and started again they would turn the camera's intrinsics and poses for a picture that is not turned so, and its tags would come out mirrored through the camera's axis. A Refresh also logs a camera that another card's entry, which shares it (the same path on the Stream Server, on the same machine or pulled as external, by any name), turns otherwise: the capture is turned once, as the card that starts it says, and each card's bases read their own entry's turn, so give the entries the same Rotate. A Linux camera is held at its frame rate in dim light: with the entry's `steady_fps` on, the default (Config tab), Start sets the camera's `exposure_dynamic_framerate` to 0 (`exposure_auto_priority` on older kernels) with `v4l2-ctl` right before FFmpeg, so the C920s, whose auto exposure would otherwise lengthen a frame in a dim room and give 15 fps for the 30 asked, keep 30 fps with a darker picture. Turn it off for a brighter picture at a lower rate; a host without `v4l2-ctl`, or a camera without either control, starts as before. A stream with an `ssh_profile` is started as an FFmpeg process inside a tmux session named `mmla-stream-<name>` on that host (H.264 to MediaMTX for `rtmp://`, `rtsp://` and `srt://` targets, raw PCM for the `udp://` and `tcp://` targets of ASR bases); a stream without one is shown as `External` and only pulled from. The name is what the stream is on its machine (the tmux session) and in the stream registry, so a name is one capture: cards that name a stream the same share it when they reach the same path on the Stream Server (or have the same target, where it goes elsewhere) and run it on the same machine, or one of them is external (an IPS and a VFA Base pulling one camera); another path, or managed entries on two machines, under that name is a name clash, checked against the `Streams` entries of every card. Such a row reads `Name clash`, and **Start** does not start it; a row whose machine runs another card's stream under its name reads `Name in use`, its **Stop** leaves that stream alone, and **Logs** says whose pane it shows. Renaming one of the two entries on its card's Config tab fixes it; its target can stay. An entry renamed while it runs leaves its capture running under the old name, listed below its card's entries to be stopped, and until it is the other card's row reads `Name in use`. A card whose config cannot be read is said so in the log, and until it can be, **Stop** leaves a capture that publishes somewhere other than the row's target alone. Before it starts one, **Start** asks the host for `tmux` and `ffmpeg`, and for what its Device list uses (`v4l2-ctl` for a camera, `arecord` for a microphone), and installs what is missing: with `apt-get` through `sudo`, answered with the SSH profile's password (on `local` with the Sudo password of System Settings), or with `brew` on a Mac. The row reads `Installing` meanwhile, a second stream on the same host waits for that install instead of starting its own, and a host still without tmux or ffmpeg starts nothing: the log says why (sudo refused the password, apt busy, ...) and what to type there by hand. A capture the console started whose `Streams` entry has since been deleted or renamed on the Config tab is listed under the config's streams as `<name>  (not in Streams)`: its FFmpeg and its tmux session are still on their host with no entry left to reach them, so the row is there to **Stop** (and **Logs**) it, takes no edits, and goes once its host has nothing left of it. Such a row comes from the stream registry, which notes every stream started from here, and is shown on the card whose app its target names, so another pipeline's stream stays on its own tab. A **Start** or **Stop** sent to a host goes on to its end when the card is refreshed or left meanwhile, notes what came of it in the stream registry, and still writes its lines into the log; a **Refresh** notes the start a host wrote down for a running stream the registry does not have (a log line says so) and notes as stopped a stream whose host has nothing left of it. **Status** is that FFmpeg, not its tmux session, which outlives it: `Exited` means FFmpeg stopped by itself (**Logs** shows why, **Start** starts it again), and **Start** waits until FFmpeg has run for three seconds, quoting its last lines when it does not. A push the Stream Server dropped does not end FFmpeg: it opens the push again every five seconds until the server takes it, and the recording goes on meanwhile, so such a row stays `Running` while its **Stream Server** column reads `○ not live` (see [Streaming](rtmp_streaming.md#devices-pushing-a-stream)). The **Stream Server** column says whether the server of System Settings receives the stream (`● live`, `○ not live`). A Mac captures through AVFoundation (`device` `0` is its first camera, `:0` its microphone), and on a Mac reached over SSH FFmpeg is started from a Terminal window on the Mac's screen, since macOS lets nothing started over SSH use the camera or the microphone; the window closes by itself once FFmpeg runs, and FFmpeg runs on without it. **Probe** decodes two seconds of the URL the bases pull (`read_target`, else `target`). A stream with `record: true` also writes a raw recording on the capture host, one file per Start, as `<record_root>/streams/capture/<YYYY-MM-DD>/<host label>/<video|audio>/<name>_<start>.<mkv|wav>`: `record_root` is `~/artifacts` on a remote host and the project's `artifacts/` for `local` unless the entry names another, the day is this console's date at Start, and the host label is the SSH profile (this machine's short name for `local`). It is filed by day and not under a session, because a stream is shared by the sessions that pull it (one after another, or several groups at once); Stop waits for FFmpeg to finalize the file and names it. A session's part of these recordings is exported from the Sessions tab (**Export**, below). **Manage** lists the recordings on each capture host with their sizes, the room left there and the file being written now, and deletes them there: **Delete File** the selected recording, **Delete Day** every recording of the selected recording's day on its host, **Delete Older Than** every recording last written longer ago than the age beside it. Each takes a second press, and the first says what would go (Delete Day names the day and the host); the file a stream is writing is never deleted. Manage copies nothing to this machine: that is the Sessions tab's Export, by session (a stream captured here, `local`, records into this machine's `artifacts/streams/capture/` in the first place). Its **Keep recordings for** sets `record_keep_days` of every stream of the card: older recordings are deleted at a stream's Start and at Refresh, and Record shows the time (`yes, 7 d`). An external stream shows `n/a` under Record: the console does not run its FFmpeg, so nothing records it on a capture host (the Stream Server does while a session that pulls it runs: **Sessions → Export**). The Collection card's own Download is for the sessions of its recorders. See the [Streaming guide](rtmp_streaming.md#recording).
- **Transform Matrix** tab (IPS only): the `transformation_matrices*.json` files produced by camera sync, each listed with whose coordinates it holds by the host's `Bases` (`transformation_matrices_<id>.json · main of room <room>`; the plain `transformation_matrices.json` is camera sync's pairs, of every room), editable as JSON, with **Sync to Host** to copy the files of the host on screen to another machine and **Sync from Host** to bring another machine's onto it (a base station's back here, or this machine's onto the base station on screen); after a Sync from Host the tab lists the files again, and the Main Camera choices of that host follow. **Delete** removes the file on screen from the host the tab edits (this machine, or the selected one) after a second press; the other hosts keep their copy, and what loaded it has no matrices until camera sync writes them again: a main's file is every base of its room and the synchronizer with that Main Camera, whose first press names them. A base of a room never takes another room's file in its place (those are other coordinates), and a synchronizer of a config with a main per room needs its Main Camera.

The server cards are different:

- **ASR Server** and **VFA Server** run the AI services with docker compose on the selected host (`docker/docker-compose.asr.yml`, `docker/docker-compose.vfa.yml`). The Launch tab lists the sub-services from the server config with a `true`/`false` toggle each; Start runs `docker compose up -d --build` for the selected ones, Stop runs `down`, Logs tails the containers. The VFA Server card also has a **Prompts** tab (the templates under `pipelines/vfa-server/prompts/`) and an **Action Schema** tab (`config/vfa/action_schemas.yml`). Both edit the files of the selected host and carry **Sync to Host** to copy them to another and **Sync from Host** to bring another's in. Its Config tab carries the `features` block of the [features endpoint](pipelines/vfa/index.md#features-endpoint-skeletons-and-gazes) (the pose model, where its weights live, the confidence thresholds), which the server reads at its next Start.
- **MLLM Server** starts `vllm serve` from `config/mllm_server.yml` in the `vfa-vllm` environment, inside a tmux session named `mllm-server`, for VFA setups that use a local vision-language model. Its Config tab edits this machine's `config/mllm_server.yml` whatever the Host selector says; **Sync to Host** sends it to the host picked, and **Sync from Host** brings that host's here.
- **IPS Intrinsics** and **IPS Transforms** run the interactive calibration and multi-camera synchronisation tools. Calibration captures a camera's checkerboard images into `pipelines/ips-base/camera_calib/cameras/<name>/` (a later capture adds to them) and writes its parameters to `Cameras.<name>` of `pipelines/ips-base/config.yml`. Below the card, **Calibration Cameras** lists the cameras of this machine that have images or parameters, with what each has (`7 image(s) · calibrated (fisheye: no) · used by base 0`). **Open Folder** shows a camera's images in the file browser, where a bad one is looked at and removed. **Delete Camera** removes its images and its parameters after a second press, and not while a base in the config uses it; other hosts keep their copy. **Sync to Host** gives the host that runs the IPS base this camera's parameters: only `Cameras.<name>` of that host's config is written, its `Bases` and `Streams` stay as they are (the Config tab's own Sync to Host copies the whole file). The host needs an IPS base config first. **Sync from Host** goes the other way and needs no camera picked: every calibrated camera of the picked host's config comes into this machine's, parameters only (the images stay on that host), and the status line says which were added, updated and unchanged. When it would replace parameters this machine already has for a camera, a first press names those cameras and writes nothing, and a second press takes the host's. This machine needs an IPS base config first. **IPS Transforms** puts a second camera in the main one's coordinates: it listens for the tag detections both bases publish, so the config's `Bases` needs the main base (`main: true`, exactly one, or one per room) and at least one other, and both bases must be running. Start refuses with that explanation when the config of the card's host has fewer, and so does `mmla ips-csync` itself.

The pipeline guides walk through each one end to end: [ASR](pipelines/asr.md), [IPS](pipelines/ips.md), [VFA](pipelines/vfa/index.md).

### Session Control

Bases and synchronizers block after start-up until they receive a START signal for their session. This leaf lists the sessions, lets you tick the pipelines, and sends **START** or **STOP** over Redis. STOP also marks the session as ended in MongoDB. The list opens on the session the base cards were last started into. The Redis and MongoDB addresses come from System Settings and are shown on the panel.

There is no host to pick here: the signal is published from this machine to that Redis, and every base subscribed to the same Redis hears it, whichever machine it runs on. What matters is therefore that all machines of a session use **one** Redis. With `Redis.host` left at `localhost`, only bases on this machine hear the signal, because a base on another machine reads `localhost` as itself; the panel warns about it. Put the host name of the machine that runs Redis into **System Settings → Redis** for a session that spans machines. While Redis has no host yet on this machine (no `config/system_services.yml`, no Redis section in it, or `<uber-server>` still there), the panel says so and sends neither START nor STOP; while MongoDB has none, STOP still goes out but cannot mark the session ended, and says so.

A typical run is therefore: start the AI servers and the system services, start the bases and synchronizers on every base station (each with the `Bases` entry its card gave it, all into one session: the cards after the first open on it), then send START from here once every window reports it is waiting, and STOP when the session is over. Every base and synchronizer the Launcher started for that session then exits by itself; the bases note in the session when they left, which is when a session that was never ended is taken to end.

## Sessions tab

A table of sessions with `Session ID`, `Experiment`, `Group`, `Status`, `Started`, `Recordings until`, `Files here` and `Source`, merged from the MongoDB `sessions` collection and from the session folders of the host the Host selector picks. The addresses come from `config/system_services.yml`; with a remote host selected and no database sections there, its pipeline config is read over SSH instead.

The table is read again every time the tab comes into view, so a session created or recorded in the Launcher is there without a press on **Refresh** (which also reconnects to the databases). The Host selector opens on **Local** and stays where it is put, whatever the Launcher does. It picks whose session folders are listed. **Local** lists those of this checkout, `artifacts/<id>/` and `collection/<id>/` with their manifests, so a session whose MongoDB document has been deleted is still on the table. **Another host** lists the session folders it holds: `artifacts/<id>/` and `collection/<id>/` of the checkout its SSH profile names, `~/artifacts/<id>/` (where the Collection recorders write, on a Raspberry Pi for instance) and the stream cuts staged under `~/artifacts/streams/.session-cuts/<id>/`. A session MongoDB knows gains `Files@<host>` in its Source, and a folder MongoDB does not know gets a row of its own. **Files here** is what the session's folders take on the disk of the host picked, `-` for none. It is measured with `du` on that host, in one SSH call per listing, after the table is up (`...` until the host answers); a host that does not answer gets a yellow line, `?` in the column and the MongoDB rows only. The database addresses come from this machine's System Settings whichever host is picked.

- **Export** gathers everything of the selected session onto this console, into `artifacts/<session>/`, each part in the layout it has always had there; `mmla ses-export <session>` does the same from a shell. `--only measurements,collection,streams,base` runs some of the parts, `--dry-run` says what would be fetched and from where and changes nothing, and `--all-profiles` also asks every SSH profile for Collection recordings, not only the hosts the session names. The progress row under the buttons names what is being fetched from where, and its **Cancel** stops the export: what arrived stays, and a transfer cut short resumes at the next press. A row without a session id is refused. The parts, in the order they run:

    - **Measurements**: one JSON file per event type (speaker recognition and transcription, IPS translation, rotation and relation, VFA actions and features) from InfluxDB into `artifacts/<session>/measurements/`, plus a text transcript, and next to them `<session>_parameters.json`: what the session ran with, from its MongoDB document. That is its experiment, group and participants, the streams its bases took, and one entry per base and synchronizer (and, in an older session, its IPS visualizer) with the flags it was started with, the values it ran with (thresholds, durations, the camera and its intrinsics, the IPS transformation matrices, the speaker profiles, the stream), its config with the secrets masked, the software version, and what its servers answered about themselves (the transcriber's model, language and diarization, the frame analyzer's models, prompt profile and pose model). The log lists the entries. A session from before the components noted this has the file without them, and the log says so. A file that comes out of InfluxDB as it was exported before counts as here already, and with InfluxDB not connected the files exported before stay as they are. See [Databases](database.md#mongodb).
    - **Collection recordings**: each recording host's session folder into `artifacts/<session>/collection/<host>/`, with the transfer of the Collection card's **Download** (staged, resumable, merged once every file has arrived, the session's `manifest.yml` updated); this machine's own recordings are in place already. The hosts are the ones Collection Start noted in the session's MongoDB document (`collection_hosts`, with each recorder's folder and device under `collection_recorders`). A session from before Start noted them goes by the hosts of the recordings its `manifest.yml` here names, and a session with neither asks every SSH profile whether it holds `artifacts/<session>/collection/`, under `~/artifacts` (where the recorders write) and under the checkout the profile names.
    - **Streams**: the session's part of each stream it used, from the Stream Server and from the machine that captured it, into `artifacts/<session>/streams/`. Which streams are the session's comes from its sources (each base notes in the session's record the stream it takes when it joins, and when it leaves), and the part is each stretch from a START to its STOP, the times the Stream Server recorded the session (its `recording_windows` in MongoDB), the same for both copies: what was recorded before the first START, while the bases started, is no part of it. A session without them (one from before 2026-10-01, or one never STARTed) takes its start to its end (a session never ended runs until its last base left, else up to now). A stream is shared by the sessions that pull it (the Stream Server records its path while one of them runs, START to STOP; the capture host records it whether or not one runs), so two sessions that overlap each get their own part of the same camera, and the microphones of another group stay out. The **Stream Server's copy** comes from MediaMTX's playback server over HTTP (no SSH; its address and ports are under **System Settings → Stream Server**), one file per unbroken stretch, as `artifacts/<session>/streams/server/<app>/<name>_<start>.mp4`. The **capture-side copy** is looked for on the capture host of every stream this console captures, whatever Record the session's bases noted (a base notes it from its own machine's config, which can differ from the one the stream was started with): what it recorded of the session's time is cut there without re-encoding (a video cut is moved back onto a keyframe, at most a second, and named after that frame), staged there under `<record_root>/streams/.session-cuts/<session>/`, fetched with the resumable transfer and removed there once it has arrived, as `artifacts/<session>/streams/capture/<host label>/<video|audio>/<name>_<start>.<mkv|wav>`; a stream captured on this machine is cut straight into place, and the session's `manifest.yml` names these folders as file sources. An external stream has the server's copy only, and so does a stream noted with Record off whose capture host holds nothing of that time or does not answer; the log says so, and says it of one its host recorded all the same. A session whose record names no stream (one from before the bases noted them, or one no base joined) has nothing to export, and the log says so: whatever was recorded while it ran is nothing it is known to have used. Every file name carries the time of its first frame, which is what the `file` source reads, so a base with `source: file` and the file's full path as `source_index` replays it. A copy already here in full is not fetched or cut again; one exported while the session was still going is shorter under the same name, so its length is checked with `ffprobe` and it is replaced by the full one. The **Recordings until** column says when the server begins to delete a session's footage (its start plus the retention set on the Stream Server card's Config tab; `kept` when nothing is ever deleted, `gone` once it has passed), and the summary line names the retention in force; the capture hosts keep theirs as long as each stream's `record_keep_days` says (Manage on the Streams tab).
    - **Base files**: what the session's bases and synchronizers wrote on the machines they ran on into `artifacts/<session>/pipelines/<pipeline>/<host>/`: their logs (`logger/`), the config they ran with (`config/`: the `config.yml`, a `<role>[_<id>].json` per component with what it ran with, the same entry it wrote into the session's document, and for IPS the `transformation_matrices_<main>.json` the base and synchronizer loaded), what they recorded (`real-time/runtime/`: an ASR base's speech segments with **Store Audio** on and the speaker profiles it recognized, the frames VFA and IPS keep) and, in a session from before the IPS visualizer was removed, its plots (`visualizations/`). A process run on this machine writes there in the first place; one started on a remote host keeps them under `artifacts/<session>/pipelines/` of the checkout its SSH profile names. Every SSH profile is asked at once what its host holds of the session, and what it holds is fetched with the resumable transfer; `real-time/temp/` (frames on their way to a server) stays there. The folder is the session's own, so nothing in its record is needed to know what to take, but a host its bases noted they ran on that no profile reached is named in the log. A file already here at the same size is not fetched again, and one of another size (a log fetched while its base still wrote it) is replaced. The session's `manifest.yml` names each host's folders, and the ASR base's `real-time/runtime/` as a file source.

    A host that does not answer over SSH, or that no longer holds what it recorded (deleted with **Delete Remote**, or past a stream's `record_keep_days`), is named in a yellow line with what of the session it held, and the export goes on with the other hosts. What it held is then looked for on the archive host (the host **Archive** sends to, below) under `artifacts/<session>/` of its checkout, and fetched from there when it is there: the Collection recordings, the stream cuts of the Stream Server and of the capture hosts, and the base files' `config/` and `logger/`. Only what did not arrive from where it was made is taken from there, never this machine's own base files, and a file from the archive host never replaces a different one here: the archive holds what this console had when **Archive** was pressed, which may be the older copy, so it goes beside it as `<name>_<archive host><ext>`. A session that names no recording host also gets each `collection/<host>/` of the archive host that no SSH profile brought. A file already here at the same size is not fetched again (from the archive host, whose ledger states each file's sha256, only with that sha256), and a clip or cut exported before counts as here once its host no longer holds it, so pressing Export again the next day fetches only what is missing. The log ends with a summary per part: the files fetched (and how many of them from the archive host), the files here already, and what is missing and why. `mmla ses-export` exits with 1 only when something that should exist (a host the session names, a folder a host was found holding, a stream it took through the Stream Server or recorded on a capture host, a host its bases noted) is not here and could not be fetched from anywhere.
- **Archive** sends the session's raw files from this console to the System Settings host (the Dashboard's host, else the Stream Server's), into `artifacts/<session>/` of its checkout, where the dashboard and replays read them; `mmla ses-archive <session>` does the same from a shell (`--host <SSH profile>` names another host, `--dry-run` says what would go and changes nothing). It runs only when pressed, since a session is often exported the day after it ran: export it first (**Export**, above), then archive, which sends this console's copy; a session with no folder here is refused. It sends `collection/`, `streams/`, `raw/`, the `config/` and `logger/` of each `pipelines/<pipeline>/<host>/` and `measurements/<session>_parameters.json` (`--with-runtime-media` adds what the bases stored); a `profiles/` folder (speaker profiles) is never sent. The files go with rsync (resumable) or scp into `<session>/.archive/incoming/` there and are moved into place once their sha256 there is the one here; a file already there with the same sum is not sent again, and a different file of the same name there is kept, this one going beside it as `<name>_<console host><ext>` (a host's `manifest.json` or a `config.yml` too: the one there may hold rows this one lacks). On that host it then cuts the session's part of the Stream Server's recordings (the paths its bases took, over the stretches its record says the server recorded them for, else from its start to its end) into `streams/server/`, rewrites the session's `manifest.json` and `manifest.yml` there with the paths the files have there (each recording gains `relpath`, `bytes`, `sha256` and `origin`; the stream cuts are listed under `stream_cuts`, apart from the recordings, which `ses-code`, `ses-align` and `ses-calibrate` read as the collection's), and sets `archive` in the session's MongoDB document: location, status (`complete`, or `partial` while a file or a stream cut is missing), files, bytes and `verified_at`. Nothing is deleted on either side. The log ends with what was sent, what was there already, what was verified, any mismatch and the stream cuts; pressing Archive again completes a partial archive. It needs an SSH profile of the archive host, and `python3` there.
- **End Session** marks a session that was left `active` as `ended`: one whose console closed, or whose bases went down, before a STOP. The end it writes is when its last base left, once every base that joined it has (where Export already takes it to end), else the latest moment the session is known to have been alive: its last measurement in InfluxDB, a base joining or leaving it, or a log its components wrote on this machine (`artifacts/<session>/pipelines/<pipeline>/<this host>/logger/`). A time from before the session began (a replay stamps its measurements with the original recording time) does not count, and only when nothing says is it now. The first press says that end and names any base that never noted leaving; the second writes it, and switches off the Stream Server's recording of the session's paths, as STOP does (so does the Collection card's Stop when it ends a session). A base that is still running is better stopped with STOP in Session Control, which ends the session too. A Collection card that starts recording into an ended session asks first, and makes it active again.
- **Delete Session** deletes the session everywhere central, in this order, stopping at the first step that fails: its archive on the archive host (the folder **Archive** writes there, `artifacts/<session>/` of that host's checkout, with the archive's ledger inside it, and the dashboard's cached report of the session when the dashboard runs there), then the dashboard's cached report on the dashboard's own host when that is another one (the host **System Settings → Dashboard** names, else the archive host), then its events in InfluxDB, then its MongoDB document. The cached report is `<session>/` in the default place, `cache/` beside `pipelines/uber-server/dashboard/flask-backend/cache.location` of its checkout, and in each folder that file lists (every process that loads the dashboard adds its `DASHBOARD_CACHE_DIR`, or the default). A listed folder where session data lies (the home folder, the checkout or a folder above either, `artifacts/` or `collection/` of the checkout, `~/artifacts`, or below one of those) is never looked in, and a `<session>/` holding anything the dashboard does not write there (a folder, a link, a file not named `*.json`, `window_features.csv` or `.tmp-*`) is left alone; the first press names the folders it looked in and why, and what it passed over. A dashboard host other than the archive host that cannot be reached blocks nothing, since the cache can be rebuilt; the log says so. A step that fails is named in red and the steps after it do not run, so the session stays on the table and a new press goes on from there. The first press reads and says, in red, what goes: the archive's path on its host with its files and size (or that there is no archive), the InfluxDB events by type, and whether MongoDB holds the document. It also says what stays: this console's own `artifacts/<session>/`, the files on the capture hosts and other machines (**Delete Files**, host by host), and the Stream Server's recordings, which the sessions that use a stream share. Deleting the archive cannot be undone, and for an imported classroom session the archive folder holds its raw videos. The second press of the same row deletes. When the archive host cannot be reached or named, or a database that System Settings name is not connected, it says so and deletes nothing. When this console is itself the archive host, its own folder is the archive and goes with it.
- **Delete Files** deletes the selected session's folders on the host the Host selector picks, and nowhere else: on Local, this checkout's `artifacts/<session>/` and `collection/<session>/`; on another host, those of its checkout, `~/artifacts/<session>/`, `~/artifacts/streams/.session-cuts/<session>/`, and the folders the session's MongoDB document names on that host (a Collection recorder's own output root, a stream's `record_root`). The first press names the host and each folder with its size, and says when a folder is the archive copy too: the host picked is the archive host, under whichever SSH profile or address reaches it, since both hosts are asked what machine they are and where the archive lies there. the second press of the same row on the same host deletes exactly those folders, each checked again on the host just before. A folder is deleted only when it is a directory named exactly the session id, letter case included (on a Mac, whose file system ignores case, a folder whose name differs in case only is another session's and stays), directly inside one of those folders as the host resolves them; a symbolic link of that name, or a file, is refused, and the folders themselves are never deleted. A capture host's recordings filed by day (Streams tab, Manage) are not a session's folder and stay. When a host stops answering partway through a delete (a Pi's Wi-Fi drops, or the delete times out), the log names the folders it said were deleted and says the rest may be partly deleted; a new first press shows what is left.

Both deletes ask first: the first press only says what would go, any other button lets the question go (also while the first press is still reading), and only a second press of the same button on the same row deletes. `mmla ses-delete <session>` prints the same as the first press of Delete Session and deletes nothing; `--yes` deletes. `mmla ses-delete <session> --files-on <host>` (`local`, or an SSH profile) does what Delete Files does on that host; an empty host is refused before anything is read. The **Delete Session** of `mmla ses-man` is the same delete: it prints the same, then asks y/N, naming the archive's path and what stays, and only `y` deletes. Its **Delete Local Files** is Delete Files on Local, which also takes `logs/<session>/`, `visualizations/<session>/` and `real-time/runtime/<session>/` below the folder of its config (where `mmla ses-ana` writes when run there), with the same checks. A row whose id names no single folder is refused.

Export's measurements need the `uber-base` extra (analytics) in the console's environment; its streams need nothing beyond the console here, and are cut on each capture host with the FFmpeg its streams run with; its Collection recordings and base files need only the SSH profiles.

## Status tab

What is running, and where: `Service`, `Host`, `Status`, `Port` and `tmux`, refreshed every five seconds while the tab is open. The `tmux` column names the tmux session a service runs in and since when (`flask · since 09-17 13:40`): the dashboard and its worker, the MLLM server, a native MediaMTX, streams and recorders. Databases and brokers are brew, systemd or docker processes and show `-`. It has nothing to do with the recording sessions of the Sessions tab. The rows come from the Launcher's own picture of the deployment, so the two tabs cannot disagree: every service is listed on **the host its card is on** (the machine System Settings name for a system service, else the host the card was last pointed at) and probed the way its sidebar marker is. The ASR and VFA servers show how many of their containers answer (`Running 4/6`). Bases and camera tools run in their own terminals and are not listed; any other tmux session on this machine is, by name.

- A service that is **not running** gets a row only when System Settings put it on a named machine: it is part of the deployment, so its being down is worth seeing. One whose saved address still reads `<uber-server>` is listed too, with the state of the port on its card's host (the placeholder is never looked up). Everything else that is stopped is counted in the summary line, and **Show all** lists it, with the host of its card.
- The five-second refresh only asks what can be asked from here (this machine, and addresses that name a machine). A service whose host has to be logged into shows `? (Refresh)` until **Refresh** runs the full pass over SSH; Refresh also looks on every reachable host for system services whose address is `localhost`. Windows hosts are skipped.
- **View Logs** shows the selected row's logs: container or brew/journald logs for system services, the tmux pane for sessions, over SSH when the row's host matches an SSH profile. For the AI servers, use **Logs** on their Launcher card.
